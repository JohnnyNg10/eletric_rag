# 业务流程图

## 一、核心业务流程

### 1.1 用户查询流程（主流程 - 阶段B）

```mermaid
graph TD
    A[用户输入查询] --> B[术语标准化]
    B --> C[笼统度评估 + 路由判断<br/>一体化LLM调用]
    C --> D[返回预处理结果<br/>含澄清选项 + 路由建议]
    D --> E[前端展示确认面板]
    E --> F{用户操作}
    F -->|选择澄清选项| G[refined_query]
    F -->|修改路由| H[user_lane覆盖]
    F -->|直接提交| I[使用原查询 + 系统路由]
    G --> J[第二次请求：执行查询]
    H --> J
    I --> J
    J --> K{实际路由决策}
    K -->|快车道 90%| PRE[元数据提取 + 查询扩展]
    K -->|慢车道 10%| L[工具调用循环]
    PRE --> M[三路并行召回]
    M --> MD[内容去重]
    MD --> N[两阶段重排]
    N --> O{召回充分?}
    O -->|是| P[LLM生成答案]
    O -->|否| Q[缺口分析<br/>提取被引用标准号]
    Q --> Q1[缺口查询改写 + 三路二次召回]
    Q --> Q2[被引用标准精确召回<br/>按 standard_no 结构化检索]
    Q1 --> Q3[合并去重 + 重新精排]
    Q2 --> Q3
    Q3 --> P
    L --> R[多步检索聚合]
    R --> P
    P --> S[引用溯源]
    S --> T[事实一致性校验]
    T --> U[返回结果给用户]
    U --> V[记录数据飞轮<br/>predicted_lane / user_lane / lane]
```

**阶段B关键变化**：
1. 术语标准化后立即进行一体化LLM调用（笼统度+路由判断）
2. 第一次请求返回预处理结果（非阻断，HTTP 200）
3. 前端展示确认面板，用户可修改路由或选择澄清选项
4. 第二次请求携带 `user_lane`（可选）执行实际检索
5. 数据飞轮记录三个字段：`predicted_lane`（LLM建议）、`user_lane`（用户覆盖）、`lane`（最终执行）

### 1.2 阶段B两次请求流程（序列图）

```mermaid
sequenceDiagram
    participant User as 用户
    participant Frontend as 前端
    participant API as API服务
    participant Preprocessor as 预处理层
    participant LLM as 豆包Pro
    participant Router as 路由层
    participant FastLane as 快车道
    participant SlowLane as 慢车道
    participant Generator as 生成层

    Note over User,Generator: 第一次请求：预处理 + 路由建议
    User->>Frontend: 输入查询
    Frontend->>API: POST /query/preprocess
    API->>Preprocessor: 术语标准化
    Preprocessor->>LLM: 一体化调用<br/>评估笼统度 + 识别缺失维度 + 路由判断
    LLM-->>Preprocessor: vagueness_score / missing_dimensions<br/>options / lane_suggestion / lane_reason
    Preprocessor-->>API: PreprocessingOutput
    API-->>Frontend: HTTP 200 + 预处理结果
    Frontend->>Frontend: 展示确认面板<br/>路由建议 + 澄清选项
    
    Note over User,Generator: 用户确认阶段
    User->>Frontend: 选择澄清选项 / 修改路由 / 直接提交
    
    Note over User,Generator: 第二次请求：执行查询
    Frontend->>API: POST /query<br/>携带 refined_query / user_lane
    API->>Preprocessor: 术语标准化（仅）
    Preprocessor-->>API: optimized_query
    
    alt user_lane 存在
        API->>API: 使用 user_lane 覆盖系统路由
    else 使用系统路由
        API->>Router: route(query, metadata)
        Router-->>API: lane = fast/slow
    end
    
    alt 快车道
        API->>FastLane: 元数据提取 + 查询改写
        FastLane->>FastLane: 三路并行召回 + 重排
        FastLane-->>API: retrieved_chunks
    else 慢车道
        API->>SlowLane: 多步工具调用循环
        SlowLane-->>API: retrieved_chunks
    end
    
    API->>Generator: 生成答案 + 引用
    Generator-->>API: answer + citations
    API->>API: 记录数据飞轮<br/>predicted_lane / user_lane / lane
    API-->>Frontend: QueryResponse
    Frontend-->>User: 显示答案
```

**关键时序**：
1. **第一次请求**：仅预处理，返回路由建议（不执行检索）
2. **用户确认**：前端展示面板，用户可修改
3. **第二次请求**：携带用户选择，执行实际检索
4. **数据飞轮**：每次查询记录 `predicted_lane`、`user_lane`、`lane` 三字段

### 1.3 快车道详细流程（含缓存层）

```mermaid
sequenceDiagram
    participant User as 用户
    participant API as API服务
    participant Router as 路由器
    participant Redis as Redis缓存
    participant FastLane as 快车道
    participant Embedder as Embedder
    participant VectorDB as Qdrant
    participant ES as Elasticsearch
    participant MySQL as MySQL
    participant Reranker as 重排器
    participant LLM as 生成模型

    User->>API: 发起查询
    API->>Router: 查询预处理（术语标准化 + 笼统度判断）
    Router->>FastLane: 路由到快车道

    FastLane->>FastLane: 元数据提取（standard_no/category 过滤条件）
    Note right of FastLane: voltage_level 暂未启用<br/>（所有文档该字段为 NULL）
    FastLane->>FastLane: 查询扩展（QueryRewriter，最多 3 个变体）

    Note over FastLane,Redis: Level 4：生成缓存命中检查（12h TTL）
    FastLane->>Redis: GET generation:{md5(query|chunks)}
    alt L4 命中
        Redis-->>FastLane: 返回缓存答案
        FastLane-->>API: cache_hit=True
        API-->>User: 展示答案（缓存，<1s）
    else L4 未命中
        Note over FastLane,Redis: Level 2：召回缓存命中检查（1h TTL）
        FastLane->>Redis: GET recall:{md5(query|filters)}
        alt L2 命中
            Redis-->>FastLane: 返回缓存召回结果
        else L2 未命中
            Note over Embedder,Redis: Level 1：Embedding 缓存（24h TTL）
            FastLane->>Embedder: encode(query)
            Embedder->>Redis: GET embedding:dense:{md5(query)}
            alt L1 命中
                Redis-->>Embedder: 返回缓存向量
            else L1 未命中
                Embedder->>Embedder: bge-large-zh-v1.5 推理
                Embedder->>Redis: SET embedding:dense:{md5(query)} TTL=24h
            end
            Embedder-->>FastLane: query_vector

            par 三路并行召回
                FastLane->>VectorDB: 向量召回 Top20（dense+sparse hybrid）
                FastLane->>ES: 关键词召回 Top20（BM25）
                FastLane->>MySQL: 结构化召回 Top10
            end
            FastLane->>FastLane: RRF 融合 + 内容去重
            FastLane->>Redis: SET recall:{md5(query|filters)} TTL=1h
        end

        Note over FastLane,Redis: Level 3：重排缓存命中检查（1h TTL）
        FastLane->>Redis: GET rerank:{md5(query|sorted_chunk_ids)}
        alt L3 命中
            Redis-->>FastLane: 返回缓存重排结果
        else L3 未命中
            FastLane->>Reranker: 粗排 Top50→Top20（bge-reranker-base）
            FastLane->>Reranker: 精排 Top20→Top8（bge-reranker-large）
            FastLane->>Redis: SET rerank:{md5(query|sorted_chunk_ids)} TTL=1h
        end

        FastLane->>FastLane: 充分性判断（规则：top分≥0.7且分差≥0.2；不足则LLM兜底，超时1.5s默认充分）

        alt 召回充分
            FastLane->>LLM: 生成答案（Top8块作为上下文）
        else 召回不充分（触发二次检索）
            FastLane->>FastLane: 缺口分析<br/>从 gaps 和 chunks 提取被引用标准号
            Note right of FastLane: ReferenceExtractor<br/>识别"应符合 GB/T 14549"类引用
            FastLane->>FastLane: 缺口查询改写（含被引用标准号）
            par 三路并行二次召回
                FastLane->>VectorDB: 向量二次召回
                FastLane->>ES: 关键词二次召回
                FastLane->>MySQL: 结构化二次召回
            end
            opt 检测到被引用标准（跨标准引用）
                FastLane->>MySQL: 按 standard_no 精确召回<br/>被引用标准内容 Top10/标准
                Note right of MySQL: 如 GB/T 14549 谐波限值表
            end
            FastLane->>FastLane: 合并原召回 + 内容去重
            FastLane->>Reranker: 精排 合并结果→Top10
            FastLane->>LLM: 生成答案（Top10块作为上下文）
        end

        LLM-->>FastLane: 返回答案
        FastLane->>Redis: SET generation:{md5(query|chunks)} TTL=12h
        FastLane->>FastLane: 提取引用标注（CitationExtractor）
        FastLane-->>API: 返回结果（cache_hit=False）
        API-->>User: 展示答案（含引用来源）
    end
```

**缓存层说明**：
| 级别 | Key | TTL | 节省操作 |
|------|-----|-----|---------|
| L4 生成缓存 | `generation:{md5(query\|chunks)}` | 12h | 跳过全部检索+生成 |
| L3 重排缓存 | `rerank:{md5(query\|sorted_ids)}` | 1h | 跳过两阶段重排 |
| L2 召回缓存 | `recall:{md5(query\|filters)}` | 1h | 跳过三路并行召回 |
| L1 Embedding 缓存 | `embedding:dense:{md5(text)}` | 24h | 跳过向量化推理 |

**跨标准引用补充检索**：当充分性判断返回不充分时，快车道会从 `gaps` 和已召回块中提取被引用标准号（如 "应符合 GB/T 14549"），并额外按 `standard_no` 结构化召回被引用标准的实际内容。这样可以避免只回答"应符合某标准"，却没有检索该标准中具体限值、表格或条款的问题。

### 1.3 慢车道流程（多跳推理）

```mermaid
graph TD
    A[慢车道入口] --> B[步骤1: 模型决策]
    B --> C{需要继续检索?}
    C -->|是| D[选择检索工具]
    D --> D1[retrieve_standard<br/>标准检索]
    D --> D2[retrieve_clause<br/>条款精确定位]
    D --> D3[list_related_standards<br/>相关标准清单]
    D1 --> E[获取结果]
    D2 --> E
    D3 --> E
    E --> F{达到步数上限3步?}
    F -->|否| B
    F -->|是| G[聚合所有结果]
    C -->|否-信息充分| G
    G --> H[LLM生成答案<br/>附推理链路]
    H --> I[返回结果]
```

**工具说明**：
- `retrieve_standard`：调用快车道三路召回（可指定标准号过滤）
- `retrieve_clause`：精确定位某标准某条款（查MySQL元数据库）
- `list_related_standards`：返回含某关键词的相关标准清单

**控制约束**：步数≤3，单步超时2s，总延迟预算8s，独立限流QPS=10

## 二、文档处理流程

### 2.1 文档入库流程（当前实现：CLI脚本）

> **当前实现**：使用 `ingest_markdown.py` + `ingest_batch.py` 直接处理Markdown文件。
> PDF转Markdown使用独立的 `pdf_to_md.py` 脚本，非自动化流水线。

```mermaid
graph TD
    A[原始PDF] --> B[pdf_to_md.py<br/>PDF转Markdown]
    B --> C[.md 文件]
    C --> D[ingest_batch.py<br/>批量入库脚本]
    D --> E{已入库?<br/>按standard_no/file_hash判断}
    E -->|是| F[跳过]
    E -->|否| G[ingest_markdown.py::ingest]
    G --> H[parse_markdown<br/>识别章节/条款/表格]
    H --> I[build_all_chunks<br/>父块≤800token + 子块≤256token + 表格块]
    I --> J[写入MySQL<br/>Document + Chunk元数据]
    I --> K[bge-large-zh-v1.5 向量化<br/>写入Qdrant dense向量]
    I --> L[写入Elasticsearch<br/>BM25全文索引]
    J --> M[入库完成·抽样验证]
    K --> M
    L --> M
```

### 2.2 智能分块策略（当前实现）

当前分块逻辑（`ingest_markdown.py::chunk_section`）：

```
.md 文件
    ↓
parse_markdown（结构识别）
    ↓
┌─────────────────────────────────┐
│  ## 标题   →  Section           │
│  ### 小节  →  clause 起始       │
│  x.y.z条款行 → clause           │
│  | 行      →  table buffer      │
└──────────────┬──────────────────┘
               ↓
build_all_chunks（按 token 限制分组）
               ↓
  ┌────────────┬───────────────┐
  │            │               │
父块          子块           表格块
≤800token    ≤256token     独立成块
多条款聚合   单条款内容     含表格标题
  │            │               │
  └────────────┴───────────────┘
               ↓
   挂载元数据（standard_no, chapter, clause）
               ↓
   并行写入 MySQL / Qdrant / Elasticsearch
```

**规划中（未实现）**：PDF版面分析自动化、语义分块、电压等级/专业分类自动提取到元数据字段（`voltage_level` 字段当前恒为NULL）。

## 四、Loop Engineering闭环流程

> ⚠️ **规划中·未实现**：以下流程为系统设计目标，当前尚未开发。

### 4.1 周优化循环（5大闭环）

```mermaid
graph LR
    A[每周定时触发<br/>Airflow DAG] --> B[数据采集<br/>日志/反馈]
    B --> C[问题诊断]
    C --> D[闭环1: Prompt优化]
    C --> E[闭环2: 术语库扩展]
    C --> F[闭环3: 难例分析]
    C --> T[闭环4: 测试集扩充]
    D --> G[闭环5: A/B测试]
    E --> G
    F --> G
    T --> G
    G --> H{效果验证}
    H -->|显著提升 >5%| I[自动全量上线]
    H -->|无显著差异 2-5%| J[人工决策]
    H -->|效果变差| K[自动回滚]
    I --> L[更新监控指标]
    J --> L
    K --> L
    L --> M[生成周报]
```

**5大闭环说明**：
| 闭环 | 目标 | 自动化策略 |
|------|------|-----------|
| 闭环1 Prompt优化 | 降低笼统度误判率 | 置信度>0.7自动注入Few-shot |
| 闭环2 术语库扩展 | 挖掘新术语/俗称 | 频次≥5自动加入，≤2自动丢弃 |
| 闭环3 难例分析 | 定位召回失败根因 | 分块/嵌入/重排/缺失分类 |
| 闭环4 测试集扩充 | 防止效果退化 | 用户好评样本自动加入 |
| 闭环5 A/B决策 | 加速迭代 | 显著差异自动全量/下线 |

**数据依赖**：`query_logs`（笼统度、策略、二次检索）、`clarification_logs`（用户选择、自定义输入）、`badcase_tracking`（难例根因）
