# 部署架构图

## 一、生产环境部署架构

```
                         ┌─────────────────┐
                         │   负载均衡器     │
                         │  (Nginx/ALB)    │
                         └────────┬────────┘
                                  │
                    ┌─────────────┴─────────────┐
                    ↓                           ↓
           ┌────────────────┐         ┌────────────────┐
           │   前端服务      │         │   后端服务      │
           │  (React/Vue)   │         │   (FastAPI)    │
           │   × 2副本       │         │   × 3副本       │
           └────────────────┘         └────────┬────────┘
                                               │
                     ┌─────────────────────────┼─────────────────────────┐
                     ↓                         ↓                         ↓
          ┌──────────────────┐    ┌──────────────────┐    ┌──────────────────┐
          │   存储层          │    │   模型服务层      │    │   任务队列        │
          └──────────────────┘    └──────────────────┘    └──────────────────┘

存储层详情：
├── Qdrant (3节点集群)
├── Elasticsearch (3节点集群)
├── MySQL (主从架构)
├── Redis (哨兵模式)
└── MinIO (分布式模式)

模型服务层：
├── 嵌入模型服务 (vLLM × 2)
├── 重排模型服务 (TorchServe × 2)
└── LLM API (豆包Pro/通义千问)

任务队列：
├── Celery Worker × 3
├── Celery Beat (定时任务)
└── Flower (监控)

监控与日志：
├── Prometheus + Grafana
├── ELK Stack
└── Jaeger
```

### 2.2 服务资源配置

| 服务 | 副本数 | CPU | 内存 | 存储 |
|-----|-------|-----|------|------|
| frontend | 2 | 0.5核 | 512MB | - |
| backend-api | 3 | 2核 | 4GB | - |
| celery-worker | 3 | 2核 | 4GB | - |
| qdrant | 3 | 4核 | 16GB | 500GB SSD |
| elasticsearch | 3 | 4核 | 16GB | 1TB SSD |

| minio | 4 | 2核 | 4GB | 2TB HDD |

**总计资源需求**：
- CPU: ~60核

## 三、网络架构

```
┌───────────────────────────────────────────────────────────┐
│                     外部网络                               │
└───────────────┬───────────────────────────────────────────┘
                ↓
         ┌──────────────┐
         │   Ingress    │ (HTTPS, 证书管理)
         └──────┬───────┘
                │
    ┌───────────┴───────────┐
    ↓                       ↓
┌─────────┐           ┌─────────┐
│ 前端SVC │           │ 后端SVC │
│ (80)    │           │ (8000)  │
└─────────┘           └────┬────┘
                           │
              ┌────────────┼────────────┐
              ↓            ↓            ↓
        ┌─────────┐  ┌─────────┐  ┌─────────┐
        │Qdrant   │  │  ES     │  │ MySQL   │
        │(6333)   │  │(9200)   │  │(3306)   │
        └─────────┘  └─────────┘  └─────────┘

内部服务通信：
- 前端 ↔ 后端：通过Ingress (HTTPS)
- 后端 ↔ 存储：通过Service (内部网络)
- 后端 ↔ 模型：通过Service (gRPC/HTTP)
```

## 四、开发环境部署 (Docker Compose)

### 4.1 服务清单
```yaml
# docker-compose.yml
services:
  frontend:
    build: ./frontend
    ports:
      - "3000:80"
    depends_on:
      - backend

  backend:
    build: ./backend
    ports:
      - "8000:8000"
    env_file:
      - .env
    depends_on:
      - mysql
      - redis
      - qdrant
      - elasticsearch

  mysql:
    image: mysql:8.0
    ports:
      - "3306:3306"
    volumes:
      - mysql_data:/var/lib/mysql

  redis:
    image: redis:7.2
    ports:
      - "6379:6379"

  qdrant:
    image: qdrant/qdrant:latest
    ports:
      - "6333:6333"
    volumes:
      - qdrant_data:/qdrant/storage

  elasticsearch:
    image: elasticsearch:8.11.0
    ports:
      - "9200:9200"
    environment:
      - discovery.type=single-node
    volumes:
      - es_data:/usr/share/elasticsearch/data

  minio:
    image: minio/minio:latest
    ports:
      - "9000:9000"
      - "9001:9001"
    command: server /data --console-address ":9001"
    volumes:
      - minio_data:/data

volumes:
  mysql_data:
  qdrant_data:
  es_data:
  minio_data:
```

### 4.2 快速启动
```bash
# 启动所有服务
docker-compose up -d

# 查看日志
docker-compose logs -f backend

# 停止服务
docker-compose down
```

## 五、数据备份策略

### 5.1 备份内容
```
定时备份（每日凌晨3点）：
├── MySQL全量备份 (mysqldump)
├── Qdrant快照备份 (snapshot API)
├── Elasticsearch快照备份 (snapshot API)
└── MinIO对象备份 (mc mirror)

保留策略：
- 每日备份保留7天
- 每周备份保留4周
- 每月备份保留12个月
```

### 5.2 备份流程
```
Kubernetes CronJob
    ↓
执行备份脚本
    ↓
压缩备份文件
    ↓
上传到对象存储 (S3/OSS)
    ↓
删除过期备份
    ↓
发送备份报告
```

## 六、扩容策略

### 6.1 应用层扩容（无状态）
```bash
# 手动扩容后端服务
kubectl scale deployment backend-api --replicas=5 -n electric-rag-prod

# 自动扩容（HPA）
kubectl autoscale deployment backend-api \
  --cpu-percent=70 \
  --min=3 --max=10 \
  -n electric-rag-prod
```

### 6.2 存储层扩容（有状态）

**Qdrant扩容**：
1. 添加新节点到集群
2. 数据自动重新分片
3. 验证集群健康状态

**Elasticsearch扩容**：
1. 添加新数据节点
2. 等待分片重新分配
3. 验证索引分布

**MySQL扩容**：
1. 读扩展：添加从库节点
2. 写扩展：分库分表（垂直/水平拆分）

## 七、灾难恢复

### 7.1 恢复优先级

| 优先级 | 服务 | RTO | RPO |
|-------|------|-----|-----|
| P0 | 后端API、Redis | 15分钟 | 0 |
| P1 | MySQL、Qdrant | 30分钟 | 1小时 |
| P2 | Elasticsearch | 1小时 | 4小时 |
| P3 | MinIO | 2小时 | 1天 |

### 7.2 恢复流程
```
1. 启动核心服务（后端API、Redis）
   → 使用降级模式（仅缓存查询）

2. 恢复MySQL
   → 从最新备份恢复
   → 应用binlog增量

3. 恢复Qdrant
   → 从快照恢复
   → 验证向量索引

4. 恢复Elasticsearch
   → 从快照恢复
   → 重建索引

5. 全面测试
   → 查询测试
   → 压力测试

6. 切换流量
   → 灰度放量
   → 监控指标
```

## 八、监控与告警

### 8.1 监控指标

**应用指标**（Prometheus采集）：
- QPS、P95延迟、错误率
- 快慢车道流量分布
- 召回率、二次检索触发率
- LLM调用次数、Token消耗

**基础设施指标**：
- CPU、内存、磁盘使用率
- 网络IO、磁盘IO
- Pod状态、重启次数

**业务指标**：
- 用户活跃度
- 查询满意度
- 文档库规模

### 8.2 告警规则

| 告警级别 | 条件 | 通知方式 |
|---------|------|---------|
| Critical | 服务不可用、P95延迟>5s | 电话+短信+企微 |
| Warning | 错误率>1%、召回率<90% | 企微+邮件 |
| Info | 磁盘使用>80%、CPU>80% | 企微 |

## 十、安全加固

### 10.1 网络安全
- 使用私有网络（VPC）
- 服务间通信使用内网
- 对外暴露仅Ingress（HTTPS）
- 配置安全组/防火墙规则

### 10.2 数据安全
- 数据库启用TLS加密传输
- 敏感字段AES-256加密存储
- 定期备份并加密备份文件
- 访问控制（RBAC）

### 10.3 应用安全
- JWT Token认证
- API限流（100次/分钟）
- SQL注入防护（ORM参数化）
- XSS防护（输入过滤+输出转义）
