## 修复概述

根据后端架构设计文档的检查，发现并修复了6个数据库设计问题，确保数据库设计与业务需求完全对齐。

## ✅ 已修复问题

### 修复1：query_logs 表补充答案字段（高优先级）

**问题**：原设计只记录查询和召回信息，缺少生成的答案内容。

**影响**：
- 无法查看历史答案
- 无法进行答案质量分析
- 用户无法查看历史对话

**修复方案**：在 `query_logs` 表中新增4个字段：

| 字段名 | 类型 | 说明 |
|-------|------|------|
| answer | TEXT | 生成的答案 |
| answer_hash | VARCHAR(64) | 答案哈希（去重检测） |
| citations | JSON | 引用来源列表 |
| has_citations | BOOLEAN | 是否有引用 |

**新增索引**：`idx_answer_hash`

---

### 修复2：DocumentMetadata 模型修正（高优先级）

**问题**：数据库定义了 `regulation` 类型，但 Pydantic 模型缺少此类型。

**影响**：代码验证会失败

**修复方案**：在 `04-后端架构设计.md` 中修正：

```python
# 修复前
doc_type: Literal["standard", "textbook", "manual"]

# 修复后
doc_type: Literal["standard", "textbook", "manual", "regulation"]
```

---

### 修复3：新增 test_cases 表（中优先级）

**问题**：Loop Engineering闭环4（测试集扩充）和评测任务缺少数据表支持。

**影响**：
- 无法持久化测试集
- 评测任务无法加载标注数据
- 难以追踪测试集版本

**修复方案**：新增测试用例表

**表结构**：

| 字段 | 类型 | 说明 |
|------|------|------|
| id | BIGINT UNSIGNED | 主键 |
| query | TEXT | 测试查询 |
| expected_chunks | JSON | 期望召回的chunk IDs |
| expected_answer | TEXT | 期望答案（可选） |
| category | VARCHAR(50) | 测试用例分类 |
| difficulty | ENUM | easy/medium/hard |
| source | ENUM | manual/badcase/user_feedback |
| is_active | BOOLEAN | 是否激活 |
| tags | JSON | 标签 |

**支持功能**：
- 评测任务自动加载测试集
- 难例自动转化为测试用例
- 用户好评样本自动加入

---

### 修复4：新增 clause_references 表（中优先级）

**问题**：design.md 提到"形成关联块组"，但缺少表存储条款引用关系。

**影响**：
- 无法自动展开引用条款
- 慢车道的 `list_related_standards` 工具无法实现
- 无法追踪标准间的引用关系

**修复方案**：新增条款引用关系表

**表结构**：

| 字段 | 类型 | 说明 |
|------|------|------|
| id | BIGINT UNSIGNED | 主键 |
| source_chunk_id | BIGINT UNSIGNED | 源条款块ID |
| target_standard_no | VARCHAR(100) | 目标标准号 |
| target_clause | VARCHAR(200) | 目标条款号 |
| target_chunk_id | BIGINT UNSIGNED | 目标块ID（如已入库） |
| reference_type | ENUM | direct/related/superseded |

**应用场景**：
- 文档解析时自动识别条款引用（如"按照3.2.1条执行"）
- 检索时自动展开关联条款
- 慢车道工具查询相关标准

---

### 修复5：chunks 表增加 related_chunk_ids 字段（低优先级）

**问题**：父子块关系只有 `parent_chunk_id`，但对于"关联块组"（同一标准的相关条款），没有字段记录平级关联关系。

**修复方案**：在 `chunks` 表中新增字段：

```sql
related_chunk_ids JSON COMMENT '关联块IDs（引用的其他条款）'
```

**应用场景**：
- 存储同一标准内的条款引用（如"按照3.2.1条"）
- 快速查询相关条款，无需JOIN
- 与 `clause_references` 表配合使用

---

### 修复6：更新 Qdrant Payload 结构

**问题**：Payload 结构需要与 chunks 表字段保持一致。

**修复方案**：在 Payload 中新增：

```python
"related_chunk_ids": [12346, 12347]  # 关联块IDs
```

**好处**：
- 向量检索时可直接获取关联块信息
- 减少数据库查询次数

## 🚀 后续建议

### 可选优化（按需实现）

1. **user_sessions 表**（低优先级）
   - 用途：持久化用户会话历史
   - 场景：需要"历史对话记录"功能时
   - 当前方案：Redis 已足够，可后续扩展

2. **document_versions 表**（低优先级）
   - 用途：追踪文档的历史版本
   - 场景：需要查看文档修订历史时
   - 当前方案：documents 表的 version 字段已够用

3. **query_logs 表分区**（性能优化）
   - 建议：按月分区（`PARTITION BY RANGE (MONTH(created_at))`）
   - 时机：数据量超过100万条时
   - 收益：加速历史查询，简化归档

### 索引优化建议

当数据量增长后，可考虑以下复合索引：

```sql
-- query_logs 表
CREATE INDEX idx_user_created ON query_logs(user_id, created_at);
CREATE INDEX idx_lane_recall ON query_logs(lane, recall_success);

-- chunks 表
CREATE INDEX idx_doc_clause ON chunks(document_id, clause);

-- badcase_tracking 表
CREATE INDEX idx_status_priority ON badcase_tracking(status, priority);
```
