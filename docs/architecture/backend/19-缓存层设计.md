# 19 - 缓存层设计

## 一、设计目标

在不改变现有召回、重排、生成逻辑的前提下，通过在关键环节插入 Redis 缓存，实现：

| 目标 | 预期收益 |
|------|----------|
| 重复查询响应提速 | 3-5s → 0.5-1s（60-80% 降低） |
| LLM / Embedding API 成本降低 | 40-55% |
| 高并发下稳定性提升 | 缓存层挡住重复请求，减少下游压力 |

---

## 二、四级缓存架构

```
用户查询
  │
  ▼
【Level 4: 生成缓存 (2h)】─── 命中 ──► 直接返回 answer + citations
  │ 未命中
  ▼
  查询预处理 / 路由
  │
  ▼
【Level 3: 重排缓存 (4h)】──── 命中 ──► 跳过重排，直接充分性判断
  │ 未命中
  ▼
【Level 2: 召回缓存 (6h)】──── 命中 ──► 跳过三路召回，直接重排
  │ 未命中
  ▼
  三路并行召回（Qdrant + ES + MySQL）
  │
  └─► 调用 Embedder（向量化查询）
        │
        ▼
      【Level 1: Embedding 缓存 (24h)】─── 命中 ──► 跳过模型推理
        │ 未命中
        ▼
        bge-large-zh-v1.5 / SPLADE 推理
```

### 命中率估算

| 场景 | 命中层级 | 节省操作 |
|------|---------|---------|
| 完全相同的查询（含相同filters） | Level 4 生成缓存 | 全部跳过 |
| 相同查询不同时间（生成缓存过期，2h后） | Level 2/3 召回+重排缓存 | 跳过三路召回和重排 |
| 不同查询，词汇有重叠 | Level 1 Embedding 缓存 | 跳过向量化推理 |
| 全新查询 | 全未命中 | 走完整流程 |

## 三、各级缓存详细设计

### Level 1：Embedding 缓存

**目标**：避免相同文本重复调用 bge-large-zh-v1.5 / SPLADE

| 属性 | 值 |
|------|-----|
| Key 规则 | `embedding:dense:{md5(text)}`<br>`embedding:sparse:{md5(text)}` |
| Value 格式 | dense: base64(float32 bytes)；sparse: JSON `{indices:[...], values:[...]}` |
| TTL | 24 小时 |
| 存储大小估算 | dense 向量 1024 维 × 4 bytes = 4KB/条；10万条 ≈ 400MB |

**适用场景**：
- 相同查询词反复出现（召回、重排均需向量化）
- 文档入库时批量向量化重用

**注意**：Key 仅由文本内容决定，与模型版本无关。**模型升级后需清空此类缓存**。

---

### Level 2：召回缓存

**目标**：相同 query + filters 跳过三路并行召回（最耗时约 200-500ms）

| 属性 | 值 |
|------|-----|
| Key 规则 | `recall:{md5(query + "\|" + json.dumps(filters, sort_keys=True))}` |
| Value 格式 | JSON 序列化的 `List[ChunkResult]`（含 chunk_id、content、score、召回来源等） |
| TTL | 1 小时 |
| 失效时机 | 有文档新增/更新时，调用 `invalidate_recall_and_generation()` 批量清除 |

**注意**：filters 参与 key 计算，因此 `{doc_type: "standard"}` 和 `{}` 是不同的缓存条目。

---

### Level 3：重排缓存

**目标**：相同查询 + 召回集合跳过重排（bge-reranker-large 推理约 300-800ms）

| 属性 | 值 |
|------|-----|
| Key 规则 | `rerank:{md5(query + "\|" + str(sorted(chunk_ids)))}` |
| Value 格式 | JSON 序列化的 `List[RerankResult]` |
| TTL | 1 小时 |

**适用场景**：同一查询触发二次检索时，原有 Top-50 的重排结果可复用。

---

### Level 4：生成缓存

**目标**：相同 query + 参考内容跳过 LLM 生成（最贵，约 1-3s）

| 属性 | 值 |
|------|-----|
| Key 规则 | `generation:{md5(query + "\|" + concat(chunk.content))}` |
| Value 格式 | JSON `{answer, citations, generation_time_ms, model}` |
| TTL | 12 小时 |
| 失效时机 | 有文档更新时批量清除 |

**注意**：chunk 内容顺序会影响 key，因此重排顺序变化会导致缓存 miss。这是预期行为，保证了答案与上下文的一致性。

## 四、集成点

### 4.1 Embedder（Level 1）

```python
# embedder.py - encode() 方法加缓存包装
def encode(self, text: str) -> np.ndarray:
    cache = get_cache_manager()

    # 先查缓存
    cached = cache.get_dense(text)
    if cached is not None:
        return cached

    # 模型推理
    vector = self.dense_model.encode(text, normalize_embeddings=True)

    # 写缓存
    cache.set_dense(text, vector)
    return vector
```

同理 `encode_sparse()` 使用 `get_sparse / set_sparse`。

---

### 4.2 FastLane（Level 2 + Level 3）

```python
# fast_lane.py - _multi_path_recall() 加召回缓存
async def _multi_path_recall(self, queries, filters, hyde_query=None):
    cache = get_cache_manager()
    main_query = queries[0]

    # Level 2: 召回缓存
    cached_recall = cache.get_recall(main_query, filters)
    if cached_recall is not None:
        return [ChunkResult(**r) for r in cached_recall]

    # 未命中，执行三路召回
    chunks = await self._recall_engine.recall(main_query, filters, hyde_query=hyde_query)

    # 写缓存（ChunkResult 序列化为 dict）
    cache.set_recall(main_query, filters, [asdict(c) for c in chunks])
    return chunks


# fast_lane.py - 重排前后加 Level 3 缓存
async def _rerank(self, query, chunks):
    cache = get_cache_manager()
    chunk_ids = [c.chunk_id for c in chunks]

    # Level 3: 重排缓存
    cached_rerank = cache.get_rerank(query, chunk_ids)
    if cached_rerank is not None:
        return [RerankResult(**r) for r in cached_rerank]

    # 未命中，执行重排
    reranked = await self.reranker.rerank(query, chunks)

    cache.set_rerank(query, chunk_ids, [asdict(r) for r in reranked])
    return reranked
```

---

### 4.3 QueryService（Level 4）

```python
# query_service.py - execute_query() 生成前加缓存
async def execute_query(self, request):
    cache = get_cache_manager()

    # Level 4: 生成缓存（在拿到最终 reranked chunks 之后）
    chunk_contents = [c.content for c in top_chunks]
    cached_gen = cache.get_generation(request.query, chunk_contents)

    if cached_gen is not None:
        return QueryResponse(
            answer=cached_gen["answer"],
            citations=cached_gen["citations"],
            cache_hit=True,
            ...
        )

    # 未命中，执行生成
    result = await generator.generate(request.query, top_chunks)

    cache.set_generation(request.query, chunk_contents, {
        "answer": result.answer,
        "citations": [asdict(c) for c in result.citations],
        "generation_time_ms": result.generation_time,
        "model": result.model,
    })
    return QueryResponse(answer=result.answer, cache_hit=False, ...)
```

## 五、缓存失效策略

### 主动失效（文档更新时）

```python
# 在文档入库/更新完成后调用
def on_document_updated(doc_id: int):
    cache = get_cache_manager()
    # 清除召回/重排/生成缓存（Embedding 缓存无需清除，向量不变）
    count = cache.invalidate_recall_and_generation()
    logger.info(f"[Cache] Invalidated {count} entries after doc_id={doc_id} updated")
```

### 被动失效（TTL 到期）

各级 TTL 设置基于"数据变化频率"和"成本"的权衡：

| 级别 | TTL | 配置项 | 理由 |
|------|-----|--------|------|
| Embedding | 24h | `CACHE_EMBEDDING_TTL=86400` | 向量几乎不变，计算成本高 |
| 召回 | 6h | `CACHE_RECALL_TTL=21600` | 比生成缓存长，L4 过期后可复用 |
| 重排 | 4h | `CACHE_RERANK_TTL=14400` | 比生成缓存长，L4 过期后可复用 |
| 生成 | 2h | `CACHE_GENERATION_TTL=7200` | TTL 最短，答案最敏感、需要新鲜度 |

## 五·五、缓存开关配置

每级缓存可独立通过环境变量禁用，不需要改代码：

```env
# .env — 四级缓存开关（true/false）
CACHE_EMBEDDING_ENABLED=true    # L1: Embedding 向量缓存
CACHE_RECALL_ENABLED=true       # L2: 三路召回结果缓存
CACHE_RERANK_ENABLED=true       # L3: 重排结果缓存
CACHE_GENERATION_ENABLED=true   # L4: LLM 生成结果缓存

# 各级 TTL（秒）— L1 ≥ L2 ≥ L3 ≥ L4，保证上层过期后下层仍可复用
CACHE_EMBEDDING_TTL=86400       # 24h
CACHE_RECALL_TTL=21600          # 6h
CACHE_RERANK_TTL=14400          # 4h
CACHE_GENERATION_TTL=7200       # 2h
```

**典型使用场景**：

| 场景 | 建议配置 |
|------|---------|
| 生产环境（标准使用） | 全部 `true`（默认） |
| 文档批量更新期间 | `CACHE_RECALL_ENABLED=false` + `CACHE_GENERATION_ENABLED=false` |
| 调试/测试（需要实时结果） | 全部 `false` |
| 节省内存（Redis 资源受限） | 仅保留 `CACHE_EMBEDDING_ENABLED=true` |
| 不信任生成结果时效性 | `CACHE_GENERATION_ENABLED=false` |

**实现方式**（各集成点统一模式）：

```python
# 以生成缓存为例，其他级别同理
if settings.CACHE_GENERATION_ENABLED:
    cached_gen = cache.get_generation(request.query, chunk_contents)
    if cached_gen is not None:
        return QueryResponse(answer=cached_gen["answer"], cache_hit=True, ...)

result = await generator.generate(...)

if settings.CACHE_GENERATION_ENABLED:
    cache.set_generation(request.query, chunk_contents, {...}, ttl=settings.CACHE_GENERATION_TTL)
```

## 六、监控指标

在 QueryService 中通过 `cache_hit` 字段统计，暴露以下指标：

| 指标 | 说明 |
|------|------|
| `cache_hit_rate_generation` | 生成缓存命中率，反映 LLM 成本节省 |
| `cache_hit_rate_recall` | 召回缓存命中率，反映检索成本节省 |
| `cache_hit_rate_embedding` | Embedding 缓存命中率，反映推理成本节省 |
| `cache_memory_used_mb` | Redis 内存占用 |
| `cache_eviction_count` | TTL 自然淘汰数量（Redis INFO 获取） |

访问路径：`GET /api/v1/metrics/cache_stats`

## 七、Redis 内存规划

| 类型 | 单条大小 | 预估条数 | 占用 |
|------|--------|--------|------|
| Embedding dense | ~4 KB | 50,000 | ~200 MB |
| Embedding sparse | ~2 KB | 50,000 | ~100 MB |
| 召回结果 | ~50 KB | 5,000 | ~250 MB |
| 重排结果 | ~10 KB | 5,000 | ~50 MB |
| 生成结果 | ~5 KB | 10,000 | ~50 MB |
| **合计** | | | **~650 MB** |

建议 Redis 配置 `maxmemory 1gb`，策略 `allkeys-lru`（内存满时淘汰最久未使用的 key）。

## 八、缓存层与现有流程的对应关系

缓存不修改任何业务逻辑，仅在关键路径前后插入 get/set 调用：

```
查询流程（含缓存插入点）：

预处理 → 路由
         │
         ├──[Level 4 GET]──► 命中 → 直接返回
         │
         ▼
    元数据提取 / 查询改写
         │
         ├──[Level 2 GET]──► 命中 → 跳到重排
         │
         ▼
    三路并行召回
    （内部调用 Embedder）
         │
         └──[Level 1 GET/SET in Embedder]
         │
         ├──[Level 2 SET]
         │
         ├──[Level 3 GET]──► 命中 → 跳到充分性判断
         │
         ▼
    两阶段重排
         │
         ├──[Level 3 SET]
         │
         ▼
    充分性判断 → 生成
         │
         ├──[Level 4 SET]
         │
         ▼
    返回结果
```
