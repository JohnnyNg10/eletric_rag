# 19 - 缓存层设计

**文档版本**: v3.0  
**最后更新**: 2026-07-16

---

## 一、设计目标

在不改变现有召回、重排、生成逻辑的前提下，通过在关键环节插入缓存，实现：

| 目标 | 预期收益 |
|------|----------|
| 重复查询响应提速 | 3-5s → 0.5-1s（60-80% 降低） |
| LLM / Embedding API 成本降低 | 40-55% |
| 语义相似查询共享缓存 | 减少"同意不同句"场景的冗余计算 |
| 高并发下稳定性提升 | 缓存层挡住重复请求，减少下游压力 |

---

## 二、缓存架构总览

### 2.1 六级缓存（含语义缓存）

> v3.0 新增：语义缓存（S 层），基于向量相似度匹配，覆盖精确匹配无法命中的"同义异句"场景。

```
用户查询
  │
  ├─ cache_strategy=semantic?
  │     │ 是
  │     ▼
  │   【S: 语义缓存 (6h) · Qdrant】
  │   余弦相似度 ≥ 0.95 + filters 完全一致
  │     │ 命中 ──► 直接返回 answer + citations
  │     │ 未命中
  │     ▼
  │   继续下方流程 ──► 生成后写入 S 层
  │
  ├─ cache_strategy=exact（默认）
  │     ▼
  ▼
【L4: 生成缓存 (2h) · Redis】────── 命中 ──► 直接返回 answer + citations
  │ 未命中
  ▼
  查询预处理 / 路由
  │
  ▼
【L3: 重排整体缓存 (4h) · Redis】── 命中 ──► 跳过重排，直接充分性判断
  │ 未命中
  ▼
  两阶段重排（粗排 + 精排）
    内部逐 chunk 先查：
  【L3.5: per-chunk 分数缓存 (4h) · Redis】── 命中 ──► 跳过该 chunk 的模型推理
  │
  ▼
【L2: 召回缓存 (6h) · Redis】────── 命中 ──► 跳过三路召回，直接重排
  │ 未命中
  ▼
  三路并行召回（Qdrant + ES + MySQL）
  内部调用 Embedder：
  【L1: Embedding 缓存 (24h) · Redis】── 命中 ──► 跳过模型推理
    │ 未命中
    ▼
    bge-large-zh-v1.5 / SPLADE 推理
```

### 2.3 命中率估算

| 场景 | 命中层级 | 节省操作 |
|------|---------|---------|
| 语义相似查询（余弦 ≥ 0.95，semantic 模式） | S | 全部跳过（包括召回、重排、生成） |
| 完全相同查询（exact 模式，L4 有效期内） | L4 | 全部跳过 |
| 相同查询不同时间（L4 过期，L2/L3 有效） | L2 + L3 | 跳过召回和重排 |
| 相同召回集合，不同 top_k | L3.5 | 跳过大部分 chunk 的模型推理 |
| 全新查询，但词汇有重叠 | L1 | 跳过向量化推理 |
| 全新查询 + 全新词汇 | 全未命中 | 走完整流程 |

## 三、各级缓存详细设计

### S：语义缓存

**目标**：覆盖精确 md5 匹配无法命中的"同义异句"查询，如"变压器差动保护整定原则"与"变压器差动保护怎么整定"。

| 属性 | 值 |
|------|-----|
| 存储后端 | Qdrant（独立 collection `semantic_query_cache`） |
| 匹配方式 | 余弦相似度 ≥ `SEMANTIC_CACHE_SIMILARITY_THRESHOLD`（默认 0.95） |
| Filters 约束 | `filters_hash`（md5）必须完全一致，保证知识库范围相同 |
| 向量来源 | L1 已计算的 `query_embedding`，零增量成本 |
| TTL | 6 小时（代码内检查 `created_at`） |
| 开关 | `SEMANTIC_CACHE_ENABLED` |
| 多轮对话 | 传入 `conversation_id` 时**自动跳过**（上下文相关，不可复用） |
| 前端控制 | `cache_strategy=semantic`（默认 `exact`，不启用 S 层） |
| 集成点 | `query_service.py`，在 L4 查找之前执行 |

**Payload 存储字段**：

| 字段 | 说明 |
|------|------|
| `query_text` | 原始查询（调试用） |
| `filters_hash` | 过滤条件 md5 |
| `filters` | 原始过滤条件（调试用） |
| `answer` | LLM 生成的答案 |
| `citations` | 引用列表 |
| `recall_results` | 召回结果（供命中后直接返回） |
| `rerank_results` | 重排结果（供命中后直接返回） |
| `created_at` | Unix 时间戳（TTL 判断） |

---

### L1：Embedding 缓存

**目标**：避免相同文本重复调用 bge-large-zh-v1.5 / SPLADE。

| 属性 | 值 |
|------|-----|
| Key（文本内容） | `embedding:dense:{model_version}:{md5(text)}`<br>`embedding:sparse:{model_version}:{md5(text)}` |
| Key（chunk_id） | `embedding:dense:id:{chunk_id}` |
| Value 格式 | dense: `base64(float32 bytes)`；sparse: JSON `{indices:[...], values:[...]}` |
| TTL | 24 小时（`CACHE_EMBEDDING_TTL=86400`） |
| 开关 | `CACHE_EMBEDDING_ENABLED` |
| 模型版本 | Key 中含 `model_version`，升级模型后自动隔离旧向量 |

---

### L2：召回缓存

**目标**：相同 query + filters + HyDE 配置 + 扩展查询，跳过三路并行召回（约 200-500ms）。

| 属性 | 值 |
|------|-----|
| Key | `recall:{md5(query + "\|" + json.dumps(filters, sort_keys=True) + "\|hyde={bool}" + "\|eq=" + sorted(expanded_queries))}` |
| Value | JSON `List[ChunkResult.model_dump()]` |
| TTL | 6 小时（`CACHE_RECALL_TTL=21600`） |
| 开关 | `CACHE_RECALL_ENABLED` |
| 集成点 | `fast_lane.py::_multi_path_recall()` |

---

### L3：重排整体缓存

**目标**：相同查询 + 相同召回集合，跳过两阶段重排（CPU 推理约 35 秒）。

| 属性 | 值 |
|------|-----|
| Key | `rerank:{md5(query + "\|" + stage + "\|" + str(top_k) + "\|" + model_version + "\|" + str(sorted(chunk_ids)))}` |
| Value | JSON `List[RerankResult.__dict__]` |
| TTL | 4 小时（`CACHE_RERANK_TTL=14400`） |
| 开关 | `CACHE_RERANK_ENABLED` |
| 集成点 | `fast_lane.py`（首轮 `top_k=8`，重试 `top_k=10`） |

---

### L3.5：per-chunk 分数缓存

**目标**：重排时对每个 chunk 的打分结果单独缓存，避免同 chunk 在不同 top_k / 重试场景中重复推理。

| 属性 | 值 |
|------|-----|
| Key | `rerank:score:{stage}:{model_version[:12]}:{md5(query)}:{chunk_id}` |
| Value | JSON 浮点数（sigmoid 归一化分数） |
| TTL | 4 小时（`CACHE_RERANK_TTL=14400`）|
| 存储位置 | `rerank.py::_compute_scores()` |

---

### L4：生成缓存

**目标**：相同 query + 参考内容，跳过 LLM 生成（约 7-10 秒）。

| 属性 | 值 |
|------|-----|
| Key | `generation:{md5(query + "\|" + concat(chunk.content))}` |
| Value | JSON `{answer, citations, generation_time_ms, model}` |
| TTL | 2 小时（`CACHE_GENERATION_TTL=7200`） |
| 开关 | `CACHE_GENERATION_ENABLED` |
| 多轮对话 | 传入 `conversation_id` 时**自动跳过**读写缓存 |

## 七、缓存失效策略

### 主动失效（文档更新时）

```python
cache.invalidate_recall_and_generation()  # 清除 recall:* / rerank:* / generation:*
# L1 Embedding 和 S 语义缓存无需清除（内容向量不变）
```

### 被动失效（TTL 到期）

| 级别 | TTL | 配置项 |
|------|-----|--------|
| S 语义缓存 | 6h | `SEMANTIC_CACHE_TTL_HOURS=6`（代码内检查） |
| L1 Embedding | 24h | `CACHE_EMBEDDING_TTL=86400` |
| L2 召回 | 6h | `CACHE_RECALL_TTL=21600` |
| L3 重排整体 | 4h | `CACHE_RERANK_TTL=14400` |
| L3.5 per-chunk 分数 | 4h | `TwoStageReranker.cache_ttl=14400` |
| L4 生成 | 2h | `CACHE_GENERATION_TTL=7200` |

TTL 层次关系：L1 ≥ L2 ≥ L3 ≥ L4，保证上层缓存过期后下层仍可复用。

## 八、缓存开关配置

```env
# .env

# 语义缓存（Qdrant）
SEMANTIC_CACHE_ENABLED=true
SEMANTIC_CACHE_SIMILARITY_THRESHOLD=0.95
SEMANTIC_CACHE_TTL_HOURS=6

# 精确缓存（Redis）
CACHE_EMBEDDING_ENABLED=true
CACHE_RECALL_ENABLED=true
CACHE_RERANK_ENABLED=true
CACHE_GENERATION_ENABLED=true

CACHE_EMBEDDING_TTL=86400
CACHE_RECALL_TTL=21600
CACHE_RERANK_TTL=14400
CACHE_GENERATION_TTL=7200
```

| 场景 | 建议配置 |
|------|---------|
| 生产环境 | 全部 `true` |
| 文档批量更新期间 | `CACHE_RECALL_ENABLED=false` + `CACHE_GENERATION_ENABLED=false` + `SEMANTIC_CACHE_ENABLED=false` |
| 调试 / 测试 | 全部 `false` |
| Redis 资源受限 | 仅 `CACHE_EMBEDDING_ENABLED=true` |

## 九、Redis 内存规划

| 类型 | 单条大小 | 预估条数 | 占用 |
|------|--------|--------|------|
| L1 dense | ~4 KB | 50,000 | ~200 MB |
| L1 sparse | ~2 KB | 50,000 | ~100 MB |
| L2 召回结果 | ~50 KB | 5,000 | ~250 MB |
| L3 重排结果 | ~10 KB | 5,000 | ~50 MB |
| L3.5 per-chunk 分数 | ~50 B | 500,000 | ~25 MB |
| L4 生成结果 | ~5 KB | 10,000 | ~50 MB |
| **合计（Redis）** | | | **~675 MB** |

S 层语义缓存存储在 Qdrant，payload 约 5-10 KB / 条，预估 10,000 条 → ~100 MB 向量索引空间（独立于 Redis）。

建议：Redis `maxmemory 1gb`，策略 `allkeys-lru`。

## 三、各级缓存详细设计

### L1：Embedding 缓存

**目标**：避免相同文本重复调用 bge-large-zh-v1.5 / SPLADE。

| 属性 | 值 |
|------|-----|
| Key（文本内容） | `embedding:dense:{model_version}:{md5(text)}`<br>`embedding:sparse:{model_version}:{md5(text)}` |
| Key（chunk_id） | `embedding:dense:id:{chunk_id}` |
| Value 格式 | dense: `base64(float32 bytes)`；sparse: JSON `{indices:[...], values:[...]}` |
| TTL | 24 小时（`CACHE_EMBEDDING_TTL=86400`） |
| 开关 | `CACHE_EMBEDDING_ENABLED` |
| 模型版本 | `bge-large-zh-v1.5`（硬编码，待配置化） |

**v2.3 改进**：Key 中新增 `model_version` 字段，模型升级后自动隔离新旧向量，避免语义漂移。

---

### L2：召回缓存

**目标**：相同 query + filters + HyDE 配置 + 扩展查询 跳过三路并行召回（单次约 200-500ms）。

| 属性 | 值 |
|------|-----|
| Key | `recall:{md5(query + "\|" + json.dumps(filters, sort_keys=True) + "\|hyde={bool}" + "\|eq=" + sorted(expanded_queries))}` |
| Value | JSON `List[ChunkResult.model_dump()]` |
| TTL | 6 小时（`CACHE_RECALL_TTL=21600`） |
| 开关 | `CACHE_RECALL_ENABLED` |
| 集成点 | `fast_lane.py::_multi_path_recall()` |

**v2.3 改进**：Key 中新增 `expanded_queries`（扩展查询列表），避免同一原始查询产生不同扩展子查询时错误命中缓存。

---

### L3：重排整体缓存

**目标**：相同查询 + 相同召回集合 跳过两阶段重排（当前 CPU 推理约 35 秒）。

| 属性 | 值 |
|------|-----|
| Key | `rerank:{md5(query + "\|" + stage + "\|" + str(top_k) + "\|" + model_version + "\|" + str(sorted(chunk_ids)))}` |
| Value | JSON `List[RerankResult.__dict__]` |
| TTL | 4 小时（`CACHE_RERANK_TTL=14400`） |
| 开关 | `CACHE_RERANK_ENABLED` |
| 集成点 | `fast_lane.py`（首轮 `top_k=8`，重试 `top_k=10`） |

**Key 中各字段含义**：

| 字段 | 说明 |
|------|------|
| `stage` | `"two_stage"`（固定值，供未来单阶段方案区分） |
| `top_k` | 实际返回数量，首轮 8，重试 10；不同则不同 key |
| `model_version` | fast_lane 当前传 `"default"`（待改进，见第五节） |
| `sorted(chunk_ids)` | 保证顺序无关性 |

---

### L3.5：per-chunk 分数缓存

**目标**：重排时对每个 chunk 的（query, content）打分结果单独缓存，避免同 chunk 在不同 top_k / 重试场景中重复推理。

| 属性 | 值 |
|------|-----|
| Key | `rerank:score:{stage}:{model_version[:12]}:{md5(query)}:{chunk_id}` |
| Value | JSON 浮点数（sigmoid 归一化分数） |
| TTL | **300 秒**（`cache_ttl` 参数，默认 5 分钟）|
| 存储位置 | `rerank.py::_compute_scores()` |

**作用机制**：`_compute_scores` 先逐 chunk 查缓存，仅对未命中的 chunk 组成 mini-batch 批量推理，命中的直接复用分数，最后合并返回完整分数列表。

---

### L4：生成缓存

**目标**：相同 query + 参考内容 跳过 LLM 生成（约 7-10 秒）。

| 属性 | 值 |
|------|-----|
| Key | `generation:{md5(query + "\|" + concat(chunk.content))}` |
| Value | JSON `{answer, citations, generation_time_ms, model}` |
| TTL | 2 小时（`CACHE_GENERATION_TTL=7200`） |
| 开关 | `CACHE_GENERATION_ENABLED` |
| 多轮对话 | 传入 `conversation_id` 时**自动跳过**读写缓存 |

**注意**：chunk 内容顺序影响 key（重排顺序变化 → key 变化 → miss）。这是预期行为，保证答案与上下文的一致性。

### 5.4 同步 Redis 阻塞 asyncio（P0）

**问题**：`CacheManager` 使用同步 `redis.Redis` 客户端，所有 `get/set` 操作在 asyncio 事件循环中同步阻塞执行，在高并发时会显著增加延迟。

**修复方案**：使用 `redis.asyncio` 改造为异步客户端

```python
import redis.asyncio as aioredis

class CacheManager:
    async def _get_raw(self, key: str) -> Optional[bytes]:
        return await self.client.get(key)
```

**状态**：⚠️ 待实施（需要改造所有调用方为 async）

## 七、缓存失效策略

### 主动失效（文档更新时）

```python
cache.invalidate_recall_and_generation()  # 清除 recall:* / rerank:* / generation:*
# L1 Embedding 缓存无需清除（内容向量不变）
```

### 被动失效（TTL 到期）

| 级别 | TTL | 配置项 |
|------|-----|--------|
| L1 Embedding | 24h | `CACHE_EMBEDDING_TTL=86400` |
| L2 召回 | 6h | `CACHE_RECALL_TTL=21600` |
| L3 重排整体 | 4h | `CACHE_RERANK_TTL=14400` |
| L3.5 per-chunk 分数 | **待修复：改为 4h** | `TwoStageReranker.cache_ttl`（当前默认 300s） |
| L4 生成 | 2h | `CACHE_GENERATION_TTL=7200` |

TTL 层次关系：L1 ≥ L2 ≥ L3 ≥ L4，保证上层缓存过期后下层仍可复用。
