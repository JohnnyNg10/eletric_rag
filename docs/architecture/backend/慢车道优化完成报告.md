## 问题背景

在测试查询 API 时，发现慢车道策略存在以下问题：

1. **LLM 决策不准确**：面对技术问题时，错误地选择 `list_related_standards`（列举标准）而非 `retrieve_standard`（语义检索）
2. **工具超时频繁**：单步超时设置为 2 秒，无法完成向量检索（实际需要 2-3 秒）
3. **总超时不足**：15 秒的总超时限制导致多步检索无法完成

---

### 2. 调整超时参数

**位置**: `backend/app/core/retrieval/slow_lane.py:56-58`

```python
# 改进前
STEP_TIMEOUT_MS = 2000
TOTAL_TIMEOUT_MS = 15000
LLM_DECISION_TIMEOUT_MS = 10000

# 改进后
STEP_TIMEOUT_MS = 5000      # 单步超时：2秒 → 5秒（适应向量检索耗时）
TOTAL_TIMEOUT_MS = 20000    # 总超时：15秒 → 20秒（支持多步检索）
LLM_DECISION_TIMEOUT_MS = 10000  # LLM 决策超时：保持 10秒
```

**理由**：
- 向量检索（VectorRecall + KeywordRecall）实际耗时 2-3 秒
- LLM 决策每次约 8-10 秒
- 2 步检索 + 2 次 LLM 决策 ≈ 2×3 + 2×10 = 26 秒
- 考虑并发优化，20 秒总超时是合理的

## 遗留问题

### 1. 总耗时略超限制
- **现象**: 实际耗时 24.1 秒，超出 20 秒总超时
- **原因**: LLM 决策（8-10 秒/次）+ 向量检索（2-3 秒/次）
- **影响**: 用户体验略差，但结果正确
- **建议**: 
  - 考虑使用更快的 LLM（如 GPT-4o-mini）进行决策
  - 或优化向量检索性能（批量查询）

### 2. 第二步检索的必要性
- **现象**: LLM 进行了 2 次 `retrieve_standard`
- **问题**: 第 1 步已经检索到 15 个高质量结果，第 2 步是否必要？
- **建议**: 在 prompt 中强调"如果已获得充分信息，应选择 sufficient"
