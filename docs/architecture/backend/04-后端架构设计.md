# 后端架构设计

## 一、FastAPI应用架构

### 1.1 分层架构

```
┌─────────────────────────────────────┐
│         API路由层 (endpoints)        │  ← HTTP请求入口
├─────────────────────────────────────┤
│         服务层 (services)            │  ← 业务逻辑编排
├─────────────────────────────────────┤
│         核心层 (core)                │  ← 检索/生成核心算法
├─────────────────────────────────────┤
│    数据访问层 (repositories/storage) │  ← 数据库/存储操作
└─────────────────────────────────────┘
```

### 1.2 请求处理流程

```
HTTP请求 → 中间件 → 路由 → 依赖注入 → 服务层 
  → 核心层 → 存储层 → 响应返回
```

#### 快车道 (fast_lane.py)
```python
class FastLaneRetriever:
    def __init__(self):
        self.query_rewriter = QueryRewriter()
        self.metadata_extractor = MetadataExtractor()
        self.multi_path_recall = MultiPathRecall()
        self.reranker = TwoStageReranker()
        self.sufficiency_checker = SufficiencyChecker()
    
    async def retrieve(self, query: str, user_context: dict = None) -> RetrievalResult:
        """
        固定流水线（确定性、可控延迟）：
        
        0. 查询预处理
           - 提取元数据过滤条件
           - 查询扩展（生成2-3个同义问法或HyDE假设文档）
        
        1. 三路并行召回（对每个扩展查询）
           - 向量召回：Qdrant混合检索（稠密+稀疏）
           - 关键词召回：Elasticsearch BM25
           - 结构化召回：MySQL精确查询（标准号/条款号）
        
        2. 两阶段重排
           - 粗排：轻量级模型，Top50 → Top20
           - 精排：bge-reranker-large，Top20 → Top5
        
        3. 召回充分性判断
           - 轻量级模型判断：Top5是否包含足够信息
        
        4. 二次检索补救（如不充分，最多1次）
           - 改写查询（补充缺失维度）
           - 重新执行召回+重排
           - 合并结果
        
        返回：Top5~8 文档块
        """
        # 0. 预处理
        filters = self.metadata_extractor.extract_filters(query)
        expanded_queries = await self.query_rewriter.rewrite_query(query, user_context)
        
        # 1. 三路召回
        all_chunks = []
        for q in expanded_queries:
            chunks = await self.multi_path_recall.recall(q, filters=filters, top_k=20)
            all_chunks.extend(chunks)
        
        # 去重
        all_chunks = self._deduplicate(all_chunks)
        
        # 2. 两阶段重排
        reranked = await self.reranker.rerank(query, all_chunks, top_k=5)
        
        # 3. 充分性判断
        is_sufficient = await self.sufficiency_checker.check(query, reranked)
        
        # 4. 二次检索
        if not is_sufficient:
            refined_query = await self.query_rewriter.refine_query(query, reranked)
            retry_chunks = await self.multi_path_recall.recall(refined_query, filters=filters, top_k=10)
            reranked = await self.reranker.rerank(query, reranked + retry_chunks, top_k=8)
        
        return RetrievalResult(chunks=reranked, lane="fast", retries=0 if is_sufficient else 1)
```

#### 慢车道 (slow_lane.py)
```python
class SlowLaneRetriever:
    def __init__(self):
        self.llm_client = LLMClient()
        self.tools = {
            "retrieve_standard": self._retrieve_standard,
            "retrieve_clause": self._retrieve_clause,
            "list_related_standards": self._list_related_standards
        }
    
    async def retrieve(self, query: str, max_steps: int = 3, timeout: int = 8000) -> RetrievalResult:
        """
        有界自适应检索（多跳推理）：
        
        适用场景：
        - 跨标准引用："GB 50057 和 DL/T 621 对接地电阻要求有何差异"
        - 多条款对比："10kV 和 35kV 配电室的安全距离分别是多少"
        - 多跳推理："某设备需满足IP54，应遵循哪些标准的哪些条款"
        
        流程：
        1. 模型决策：是否需要继续检索、调用哪个工具、工具参数
        2. 执行工具调用（最多3步，单步超时2s）
        3. 模型评估：信息是否充分
        4. 聚合所有步骤的检索结果
        
        返回：聚合的文档块 + 推理链路
        """
        results = []
        reasoning_steps = []
        
        for step in range(max_steps):
            # 模型决策
            decision = await self.llm_client.decide_next_action(
                query=query,
                current_results=results
            )
            
            if decision["action"] == "sufficient":
                break
            
            # 调用工具
            tool_name = decision["tool"]
            tool_params = decision["params"]
            
            try:
                tool_result = await self.tools[tool_name](**tool_params)
                results.append(tool_result)
                reasoning_steps.append(f"步骤{step+1}: {tool_name}({tool_params})")
            except Exception as e:
                reasoning_steps.append(f"步骤{step+1}: 失败 - {e}")
                break
        
        return RetrievalResult(
            chunks=self._aggregate_results(results),
            lane="slow",
            steps=len(results),
            reasoning=reasoning_steps
        )
    
    async def _retrieve_standard(self, query: str, standard_ids: List[str] = None, **kwargs):

        工具1：调用快车道检索（带标准号过滤）
        用于：需要从特定标准中检索内容
        """
        pass

        工具2：精确定位某标准某条款
        用于：模型识别出明确的标准号和条款号
        调用：MySQL元数据库直接查询
        """
        pass
    
    async def _list_related_standards(self, keyword: str, category: str = None):
```

#### 元数据提取与过滤 (metadata_extractor.py)
```python
class MetadataExtractor:
    def extract_filters(self, query: str) -> dict:
        """
        从查询中提取元数据过滤条件（前置过滤）：
        - 电压等级：10kV、35kV、110kV、220kV等
        - 标准号：GB 50057、DL/T 621等
        - 专业分类：配电、变电、继保、高压等
        - 设备类型：变压器、开关柜、电缆等
        
        返回 Qdrant Payload 过滤条件字典
        """
        filters = {}
        
        # 提取电压等级
        voltage_pattern = r'(\d+)kV'
        if match := re.search(voltage_pattern, query):
            filters['voltage_level'] = f"{match.group(1)}kV"
        
        # 提取标准号
        standard_pattern = r'(GB|DL/T|NB)\s*\d+'
        if match := re.search(standard_pattern, query):
            filters['standard_no'] = match.group(0)
        
        # 提取专业分类（基于关键词）
        category_keywords = {
            '配电': ['配电室', '配电柜', '配电系统'],
            '变电': ['变电站', '变压器'],
            '继保': ['继电保护', '保护装置']
        }
        for category, keywords in category_keywords.items():
            if any(kw in query for kw in keywords):
                filters['category'] = category
                break
        
        return filters
```

### 5.3 Loop Engineering 闭环优化任务

**职责**：持续优化系统效果，自动迭代

#### Prompt自动迭代
```python
@celery_app.task
def prompt_optimization_loop():
    """
    每周Prompt优化任务（Airflow DAG）：
    
    1. 数据采集（过去7天）：
       - 误判case：触发澄清但用户跳过后成功
       - 漏判case：未触发澄清但召回失败
    
    2. 自动筛选高质量样本：
       - 使用LLM评估样本质量（置信度评分）
       - 高置信度（>0.7 且频次≥3）→ 自动注入Few-shot
       - 边界case（0.5-0.7）→ 人工审核队列
       - 低置信度（<0.5）→ 自动丢弃
```

### 9.2 缓存策略

#### 多级缓存架构
```python
class MultiLevelCache:
    def __init__(self):
        self.l1 = {}  # 本地内存（超高频，5分钟TTL）
        self.l2 = redis_client  # Redis短期（高频，1小时TTL）
        self.l3 = redis_client  # Redis长期（中频，24小时TTL）
    
    async def get(self, key: str):
        """三级缓存查询"""
        # L1: 进程内存
        if key in self.l1:
            return self.l1[key]
        
        # L2: Redis短期
        if value := await self.l2.get(f"hot:{key}"):
            self.l1[key] = value
            return value
        
        # L3: Redis长期
        if value := await self.l3.get(f"warm:{key}"):
            await self.l2.setex(f"hot:{key}", 3600, value)
            return value
        
        return None
    
    async def set(self, key: str, value, frequency: str = "medium"):
        """根据访问频率设置不同TTL"""
        if frequency == "high":
            self.l1[key] = value
            await self.l2.setex(f"hot:{key}", 3600, value)
        elif frequency == "medium":
            await self.l2.setex(f"hot:{key}", 3600, value)
        else:
            await self.l3.setex(f"warm:{key}", 86400, value)
```

**缓存应用**：
- **查询结果缓存**：`query:{hash(query)}` → 1小时TTL
- **提问优化缓存**：`vagueness:{hash(query)}` → 1小时TTL（目标命中率>60%）
- **向量缓存**：`vector:{hash(text)}` → 24小时TTL
- **文档块缓存**：`chunk:{chunk_id}` → 永久（直到文档更新）

#### LLM调用优化
```python
class LLMCallOptimizer:
    async def call_with_cache_and_fallback(self, prompt: str, cache_key: str):
        """
        LLM调用三级降级机制：
        
        Level 1: 优先从缓存读取（Redis）
        Level 2: 调用LLM（带超时和重试）
        Level 3: 降级到规则引擎
        """
        # Level 1: 缓存
        if cached := await redis.get(cache_key):
            metrics.increment("llm_cache_hit")
            return cached
        
        # Level 2: LLM调用
        try:
            result = await llm_client.call(prompt, timeout=200, max_retries=1)
            await redis.setex(cache_key, 3600, result)
            return result
        except (Timeout, APIError) as e:
            logger.warning(f"LLM degradation: {e}")
            metrics.increment("llm_degradation")
            
            # Level 3: 规则引擎降级
            return self.rule_based_fallback(prompt)
```

- 累计日成本（实时更新）
- 缓存命中率（L1/L2/L3分别统计）

## 十一、关键设计决策说明

### 11.1 为什么需要快慢双通道？

**快车道**：
- 覆盖90%+查询（明确、单一标准）
- 固定流水线，延迟可控（P95 < 3s）
- 满足高并发SLA（QPS ≥ 50）

**慢车道**：
- 覆盖<10%复杂查询（多跳、对比、交叉）
- 自适应检索，准确率优先
- 独立限流，不拖垮快车道

### 11.2 为什么需要召回充分性判断？

**问题**：三路召回后，Top5可能不包含足够信息（首轮漏召回）

**解决**：
- 增加充分性判断 + 二次检索（最多1次）
- 在不破坏延迟SLA前提下，补救漏召回问题
- 预期提升召回率5-10%

### 11.3 为什么需要Loop Engineering？

**问题**：系统效果会随时间衰退（新术语、新标准、用户习惯变化）

**解决**：
- 自动从线上流量挖掘优化动力
- Prompt迭代、术语扩展、难例驱动优化
- 预期6个月内召回率从92%提升至95%+
