# 阶段C备选方案：端到端预处理微调模型

> **定位**：用单一生成式小模型替换阶段B的大模型LLM调用，完整输出预处理层所有字段  
> **对比主方案**：[16-阶段C-路由微调模型设计.md](./16-阶段C-路由微调模型设计.md)（编码器分类+KB模板）  
> **撰写日期**：2026-07-10

---

## 一、方案对比

### 1.1 主方案 vs 备选方案

| 维度 | 主方案（16文档） | 备选方案（本文档） |
|------|----------------|-------------------|
| **模型类型** | 编码器（RoBERTa 110M） | 生成模型（Qwen2.5-1.5B） |
| **任务拆分** | 编码器分类 + KB模板生成 | 端到端统一生成 |
| **输出能力** | 分类/回归 + 模板拼装 | 完整JSON结构化输出 |
| **延迟** | <100ms | ~200ms（量化后~120ms） |
| **训练数据需求** | 1000条分类标签 | 1000条完整JSON输出 |
| **options质量** | 模板化，不够灵活 | 自然流畅，覆盖边界情况 |
| **训练难度** | 低（分类任务） | 中（结构化生成） |
| **部署复杂度** | 低（transformers） | 中（需vLLM或llama.cpp） |

### 1.2 为什么需要备选方案？

主方案的**核心限制**：
- `options[].label` 和 `options[].refined_query` 依赖模板拼装，对于多维度交叉的复杂查询（如"高海拔地区的110kV变电站GIS设备接地要求"）模板会生成机械化填空句
- `lane_reason` 用分段模板，无法覆盖所有路由理由的细微差别
- KB聚合只覆盖 `standard_series`，其余7个维度仍是模板

备选方案优势：
- **端到端学习**：模型在训练时学习如何生成自然的澄清选项和路由理由
- **灵活性**：可以根据查询上下文动态调整选项描述
- **未来扩展性**：同一个模型可以继续微调用于其他生成任务

## 二、模型架构

### 2.1 基座模型选择

**推荐**：Qwen2.5-1.5B-Instruct（阿里千问1.5B指令版）

| 模型 | 参数量 | 推理延迟 | 优势 | 劣势 |
|------|--------|---------|------|------|
| **Qwen2.5-1.5B-Instruct** | 1.5B | ~200ms<br/>（Q4量化~120ms） | 指令遵循好，支持结构化输出，中文能力强 | 比编码器慢2倍 |
| Qwen2.5-3B-Instruct | 3B | ~400ms | 质量更高 | 超出延迟预算（目标<200ms） |
| Qwen2.5-0.5B-Instruct | 0.5B | ~60ms | 极快 | 结构化输出不稳定，易生成非法JSON |
| MiniCPM-2B | 2B | ~250ms | 端侧优化 | 中文指令遵循略弱 |

**不用7B的原因**：
- 7B量化后推理~300-400ms，超出延迟预算
- 预处理任务复杂度低，1.5B足够

## 三、训练方案

### 3.1 数据准备

#### 数据来源

**阶段B数据飞轮 + 人工校正**

```sql
-- 提取阶段B积累的完整输出
SELECT
    q.normalized_query AS query,
    q.vagueness_score,
    c.missing_dimensions AS missing_dimension_keys,
    q.predicted_lane AS lane_suggestion,
    q.lane_confidence,
    -- 以下字段需要补充
    NULL AS lane_reason,          -- 阶段B未记录（需从LLM日志提取或人工标注）
    NULL AS options               -- 阶段B未记录options文本（需人工标注）
FROM query_logs q
LEFT JOIN clarification_logs c ON q.id = c.query_log_id
WHERE q.predicted_lane IS NOT NULL
  AND q.vagueness_score IS NOT NULL
ORDER BY q.created_at DESC;
```

**问题**：阶段B的数据飞轮只记录了分类标签，**没有记录LLM生成的文本**（`lane_reason`和`options`）。

**解决方案**：

1. **从LLM日志提取**（如果阶段B有保存LLM响应）：
   ```python
   # 从Redis缓存或日志文件提取
   llm_response = get_llm_response_from_logs(query_log_id)
   lane_reason = llm_response['lane_reason']
   options = llm_response['options']
   ```

2. **人工标注**（如果LLM日志未保存）：
   - 对1000条样本，人工编写 `lane_reason` 和 `options`
   - 成本：~2000元（2元/条）
   - 时间：2-3周

3. **用豆包Pro批量生成**（辅助方案）：
   - 对未标注样本，用阶段B的LLM批量生成文本字段
   - 人工抽查10%，质量合格率>90%则采纳
   - 成本：1000条 × 0.01元 = 10元

#### 数据格式转换

从阶段B数据库记录转换为训练样本的完整流程。

**步骤1：从数据库提取原始数据**


**步骤3：计算strategy字段**

```python
# 根据 vagueness_score 计算 strategy（与阶段B逻辑一致）
def compute_strategy(vagueness_score: float) -> str:
    if vagueness_score > 0.7:
        return "clarify_required"
    elif vagueness_score > 0.5:
        return "clarify_optional"
    elif vagueness_score > 0.3:
        return "suggest"
    else:
        return "none"

complete_data["strategy"] = compute_strategy(0.70)  # "clarify_optional"
```

**步骤4：转换为训练样本（Instruction Tuning格式）**

```python
import json

# 固定的系统指令（所有样本共用）
INSTRUCTION = """你是电力标准知识库的查询预处理专家。分析用户查询，输出JSON格式的预处理结果。

任务：
1. 评估笼统度（0-1分，0=非常明确，1=极度笼统）
2. 识别缺失维度（从以下枚举中选择）：
   - voltage_level: 电压等级
   - equipment_type: 设备类型
   - application_scene: 应用场景
   - neutral_grounding: 中性点接地方式
   - capacity_range: 容量范围
   - install_env: 安装环境
   - standard_series: 标准系列
   - protection_type: 保护类型
3. 根据笼统度判断策略：
   - none: 0-0.3明确
   - suggest: 0.3-0.6轻度笼统
   - clarify_optional: 0.6-0.8中度笼统
   - clarify_required: 0.8-1.0严重笼统
4. 生成澄清选项（strategy非none时）：
   - label: 5-12字简短标题
   - refined_query: 15-30字完整改写查询
5. 判断路由（fast/slow）及理由：
   - fast: 明确标准号/条款号，或单一维度查询
   - slow: 对比/差异/多跳推理/涉及多个标准的关联查询

输出JSON schema（严格遵守）：
{
  "vagueness_score": float (0-1),
  "strategy": "none" | "suggest" | "clarify_optional" | "clarify_required",
  "missing_dimension_keys": [string],
  "options": [
    {
      "label": string,
      "refined_query": string
    }
  ],
  "lane_suggestion": "fast" | "slow",
  "lane_confidence": float (0-1),
  "lane_reason": string
}

注意：
1. missing_dimension_keys必须从上述8个枚举中选择
2. strategy为none时，options为空数组[]
3. lane_reason需清晰说明为什么选择该路由
"""

# 构造输入
input_text = f"查询：{complete_data['query']}"

# 构造输出（完整的JSON字符串）
output_json = {
    "vagueness_score": complete_data["vagueness_score"],
    "strategy": complete_data["strategy"],
    "missing_dimension_keys": complete_data["missing_dimension_keys"],
    "options": complete_data["options"],
    "lane_suggestion": complete_data["lane_suggestion"],
    "lane_confidence": complete_data["lane_confidence"],
    "lane_reason": complete_data["lane_reason"]
}
output_text = json.dumps(output_json, ensure_ascii=False, indent=2)

# 最终训练样本
training_sample = {
    "instruction": INSTRUCTION,
    "input": input_text,
    "output": output_text
}

# 保存为JSONL格式（每行一个样本）
with open("preprocess_e2e_train.jsonl", "a", encoding="utf-8") as f:
    f.write(json.dumps(training_sample, ensure_ascii=False) + "\n")
```

**数据质量要求**

训练样本必须满足以下约束（模型训练时会验证）：

1. **JSON格式有效性**：`output` 必须是合法的JSON字符串
2. **missing_dimension_keys枚举约束**：只能包含8个预定义维度的key
3. **strategy与vagueness_score一致性**：
   - `none`: 0 ≤ score ≤ 0.3
   - `suggest`: 0.3 < score ≤ 0.6
   - `clarify_optional`: 0.6 < score ≤ 0.8
   - `clarify_required`: 0.8 < score ≤ 1.0
4. **strategy与options一致性**：`strategy="none"` 时 `options` 必须为空数组
5. **lane_suggestion枚举约束**：只能是 `"fast"` 或 `"slow"`
6. **lane_confidence范围**：0 ≤ confidence ≤ 1
7. **options长度约束**：
   - `label`: 5-20字符
   - `refined_query`: 15-50字符

```python
                    "label": {"type": "string", "minLength": 5, "maxLength": 20},
                    "refined_query": {"type": "string", "minLength": 15, "maxLength": 50}
                },
                "required": ["label", "refined_query"]
            }
        },
        "lane_suggestion": {"enum": ["fast", "slow"]},
        "lane_confidence": {"type": "number", "minimum": 0, "maximum": 1},
        "lane_reason": {"type": "string", "minLength": 10}
    },
    "required": [
        "vagueness_score", "strategy", "missing_dimension_keys",
        "options", "lane_suggestion", "lane_confidence", "lane_reason"
    ]
}

def validate_training_sample(sample: dict) -> tuple[bool, str]:
    """验证训练样本的格式和约束"""
    try:
        # 1. 解析output JSON
        output = json.loads(sample["output"])
        
        # 2. JSON Schema验证
        jsonschema.validate(output, OUTPUT_SCHEMA)
        
        # 3. strategy与vagueness_score一致性
        score = output["vagueness_score"]
        strategy = output["strategy"]
        if strategy == "none" and not (0 <= score <= 0.3):
            return False, f"strategy=none但score={score}不在[0,0.3]"
        if strategy == "suggest" and not (0.3 < score <= 0.6):
            return False, f"strategy=suggest但score={score}不在(0.3,0.6]"
        if strategy == "clarify_optional" and not (0.6 < score <= 0.8):
            return False, f"strategy=clarify_optional但score={score}不在(0.6,0.8]"
        if strategy == "clarify_required" and not (0.8 < score <= 1.0):
            return False, f"strategy=clarify_required但score={score}不在(0.8,1.0]"
        
        # 4. strategy与options一致性
        if strategy == "none" and len(output["options"]) > 0:
            return False, f"strategy=none但options非空"
        
        return True, "验证通过"
    
    except json.JSONDecodeError as e:
        return False, f"JSON解析失败: {e}"
    except jsonschema.ValidationError as e:
        return False, f"Schema验证失败: {e.message}"
    except Exception as e:
        return False, f"未知错误: {e}"

# 批量验证训练集
def validate_dataset(jsonl_path: str):
    valid_count = 0
    total_count = 0
    
    with open(jsonl_path, "r", encoding="utf-8") as f:
        for line_num, line in enumerate(f, 1):
            total_count += 1
            sample = json.loads(line)
            is_valid, message = validate_training_sample(sample)
            
            if not is_valid:
                print(f"[行{line_num}] 验证失败: {message}")
                print(f"  查询: {sample['input']}")
            else:
                valid_count += 1
    
    print(f"\n验证完成: {valid_count}/{total_count} 通过")
    return valid_count == total_count

# 使用
validate_dataset("preprocess_e2e_train.jsonl")
```

### 5.2 服务化

```python
# app/core/preprocessing/query_optimizer.py

class EndToEndOptimizer(QueryOptimizer):
    def __init__(self):
        self.model = Llama("models/qwen2.5-1.5b-preprocess.gguf")
        self.instruction = "..."  # 固定的系统指令
    
    async def optimize(self, query: str) -> OptimizationResult:
        prompt = self._build_prompt(query)
        
        # 调用模型生成
        response = await asyncio.to_thread(
            self.model,
            prompt,
            max_tokens=512,
            temperature=0.3
        )
        
        # 解析JSON
        try:
            result_dict = json.loads(response['choices'][0]['text'])
        except json.JSONDecodeError as e:
            logger.error(f"JSON parse failed: {e}, fallback to rule-based")
            return await self._rule_based_optimize(query)
        
        # 构造 OptimizationResult
        return self._dict_to_result(result_dict)
```

**降级策略**：JSON解析失败时自动降级到规则方案。

### 5.3 与主方案的混合部署

```python
class HybridOptimizer:
    def __init__(self):
        self.use_e2e = os.getenv("USE_E2E_MODEL", "false") == "true"
        self.e2e_optimizer = EndToEndOptimizer()
        self.encoder_optimizer = EncoderOptimizer()  # 主方案
    
    async def optimize(self, query: str) -> OptimizationResult:
        if self.use_e2e:
            return await self.e2e_optimizer.optimize(query)
        else:
            return await self.encoder_optimizer.optimize(query)
```

**A/B测试**：10%流量走端到端模型，对比主方案的options自然度和延迟。

## 九、与主方案的选择建议

### 选择主方案（编码器+模板）的场景：

1. **对延迟极度敏感**：需要<100ms，不能接受120-200ms
2. **训练数据准备困难**：阶段B未保存文本字段，人工标注成本过高
3. **部署资源有限**：只有单张RTX 3060，显存<4GB
4. **options质量要求不高**：模板化选项可接受

### 选择备选方案（端到端生成）的场景：

1. **options质量要求高**：需要自然流畅的澄清选项，覆盖复杂交叉维度
2. **延迟预算宽松**：可接受120-200ms延迟
3. **训练数据可得**：阶段B保存了LLM日志，或愿意投入人工标注
4. **未来扩展性**：同一个模型可继续微调用于其他生成任务（如查询改写）

### 推荐策略

**渐进式路线**：

1. **短期（1-2月）**：先上线主方案（编码器+模板）
   - 验证分类任务准确率
   - 收集用户对options质量的反馈
   - 评估模板方案是否满足需求

2. **中期（3-6月）**：如options质量不足，启动备选方案
   - 利用主方案上线后的数据飞轮积累更多样本
   - 补充标注文本字段
   - 训练端到端模型

3. **长期（6+月）**：两个方案并存
   - 简单查询（单维度）：主方案（快）
   - 复杂查询（多维度交叉）：备选方案（质量高）
   - 根据查询复杂度动态路由
