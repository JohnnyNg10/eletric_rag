# 阶段 B：预处理路由一体化设计

> 定位：用现成大模型跑通"后确认"交互范式，同时积累训练数据，为阶段 C 微调小模型铺路  
> 前置阅读：[14-预处理路由优化分析.md](./14-预处理路由优化分析.md)  
> 撰写日期：2026-07-10

---

## 一、阶段 B 与阶段 C 的关系

阶段 B 和阶段 C 的**交互模式完全相同**，唯一区别是推理主体：

```
阶段 B：原始查询 → 现成大模型（豆包/通义）→ 结构化输出 → 用户后确认
阶段 C：原始查询 → 微调小模型               → 结构化输出 → 用户后确认
```

阶段 B 本质上是用大模型模拟阶段 C，同时完成两件事：

1. **验证交互范式**：确认"用户后确认"是否被接受。如果用户根本不看路由建议直接提交，阶段 C 的数据飞轮就不成立，需要重新设计交互。

2. **生产训练数据**：大模型输出 + 用户纠正行为 = 监督信号，替代人工标注。积累 1000-2000 条后，阶段 C 才有底气启动微调。

## 二、与当前方案的对比

### 当前方案（阶段 A）

```
用户输入
  ↓
术语标准化
  ↓
LLM 笼统度评估 + 澄清选项生成          ← 4000ms，输出澄清选项
  ↓ (笼统度高)
[阻断/非阻断 用户交互]                  ← 用户等待/选择
  ↓ (用户选择或跳过后二次请求)
路由决策（关键词规则）                  ← 1ms，只有 fast/slow
  ↓
召回
```

**问题**：
- 用户交互阻断在流程中间，路由信息被藏在后面，用户看不到
- 路由结果对用户不透明，用户无法纠正误判
- 澄清完成后的路由依然是关键词规则，准确率有限
- 积累的日志里没有路由反馈，无法判断路由质量

### 阶段 B 方案

阶段 B 同样是两次请求，但两次请求的语义完全不同于阶段 A：

```
【第一次请求】用户提交查询
  ↓
术语标准化（词典，保持不变）             ← ~5ms
  ↓
一体化 LLM 调用                         ← ~4200ms（增加路由判断约 200ms）
  输出：笼统度 + 澄清维度（枚举key）+ 路由建议
  ↓
KB 填充澄清选项具体值                   ← ~50ms（ES 聚合，仅对可聚合维度）
  ↓
返回预处理结果，前端展示确认面板
  ┌────────────────────────────────────────┐
  │  系统建议                              │
  │  路由：快车道  [切换为慢车道]          │
  │  理由：单维度查询，无需多跳推理        │
  │                                        │
  │  补充信息（可选）                      │
  │  ○ 10kV 配电装置（GB 50053，23篇）    │
  │  ○ 35kV 配电装置（DL/T 5352，18篇）   │
  │  ● 跳过，使用原始查询                  │
  │                             [提交查询] │
  └────────────────────────────────────────┘

【第二次请求】用户确认/修改后提交
  ↓
服务层读取 user_lane（若不为 null 则覆盖 Router 输出）
  ↓
召回 + 生成
```

**与阶段 A 的本质区别**：

| 对比项 | 阶段 A | 阶段 B |
|--------|--------|--------|
| 第一次请求返回内容 | 澄清选项（或直接召回） | 预处理结果 + 路由建议（始终返回，非报错） |
| 第一次请求 HTTP 状态 | 笼统时返回 400 | 始终返回 200 |
| 第二次请求触发时机 | 用户选完澄清选项 | 用户确认面板后点提交 |
| 清晰查询的请求次数 | 1 次（直接召回） | 2 次（预处理 + 召回） |
| 笼统查询的请求次数 | 2 次 | 2 次 |

> 注意：清晰查询从阶段 A 的 1 次变为阶段 B 的 2 次，是为了让路由建议对用户可见、积累路由反馈数据。如果产品上不需要展示确认面板（例如置信度高的查询），可以在前端直接跳过面板自动提交第二次请求，用户感知仍是 1 次交互。

**改变**：
- 路由建议对用户可见，用户可以纠正
- 澄清维度用预定义枚举，LLM 只需分类而非自由生成
- 第一次请求不再用 400 表示"需要澄清"，改用正常 200 + 结构化响应

## 三、LLM 调用设计

### 3.1 输入输出规范

阶段 B 将当前的笼统度评估 + 路由决策合并为一次 LLM 调用，扩展现有的 `_llm_optimize()` 方法。

**输入**：术语标准化后的查询（字符串）

**输出结构**（在现有基础上新增路由相关字段）：

```json
{
  "vagueness_score": 0.65,
  "strategy": "clarify_optional",
  "missing_dimensions": ["voltage_level"],
  "options": [
    {
      "label": "10kV配电装置安全距离",
      "refined_query": "10kV配电装置与建筑物及各类设备的安全净距要求"
    }
  ],
  "lane": "fast",
  "lane_confidence": 0.82,
  "lane_reason": "单一维度查询，包含具体设备类型，无对比或多跳需求"
}
```

新增字段说明：

| 字段 | 类型 | 说明 |
|------|------|------|
| `lane` | `"fast" \| "slow"` | 路由建议 |
| `lane_confidence` | float 0-1 | 置信度，<0.6 时前端标黄提示用户注意 |
| `lane_reason` | string | 路由理由，面向用户的可读文本 |

### 3.2 missing_dimensions 改为枚举

当前实现中 `missing_dimensions` 是 LLM 自由生成的文本（如"缺少电压等级"），阶段 B 改为从预定义维度表中选择，输出枚举 key：

```python
POWER_CLARIFICATION_DIMS = {
    "voltage_level":      "电压等级",
    "equipment_type":     "设备类型",
    "application_scene":  "应用场景",
    "neutral_grounding":  "中性点接地方式",
    "capacity_range":     "容量范围",
    "install_env":        "安装环境",
    "standard_series":    "标准系列",
    "protection_type":    "保护类型（继保）",
}
```

LLM 输出示例：`"missing_dimensions": ["voltage_level", "application_scene"]`

好处：输出格式稳定，为阶段 C 提供一致的标注标签，也使 ES 聚合查询可以按 key 直接映射到对应的 DB 字段。

### 3.3 澄清选项 KB 填充

KB 填充分两种情况处理，**不引入第二次 LLM 调用**：

**可聚合维度**（ES/DB 有对应字段）：ES 直接聚合该字段的实际值，构造选项，文档数量来自真实统计。

**不可聚合维度**（无 DB 字段）：退化为 LLM 在第一次调用中直接生成 options 文本，不依赖 KB，但标注为"建议"而非"已验证"。

对照 `06-数据模型设计.md`，各维度的当前可用性：

| 维度 key | DB/ES 字段 | 当前可用？ | 说明 |
|----------|-----------|----------|------|
| `voltage_level` | `documents.voltage_level`、ES `voltage_level` | ❌ 暂不可用 | 该字段当前恒为 NULL（PDF 转 Markdown 流程未提取），阶段 B 退化为 LLM 生成 |
| `standard_series` | `documents.standard_no` 前缀 | ✅ 可用 | 按 standard_no 前缀（GB/DL/NB）聚合 |
| `equipment_type` | 无独立字段 | ❌ | 退化为 LLM 生成 |
| `application_scene` | 无独立字段 | ❌ | 退化为 LLM 生成 |
| `neutral_grounding` | 无独立字段 | ❌ | 退化为 LLM 生成 |
| `capacity_range` | 无独立字段 | ❌ | 退化为 LLM 生成 |
| `install_env` | 无独立字段 | ❌ | 退化为 LLM 生成 |
| `protection_type` | `documents.category`='继保' | 部分可用 | 只能区分是否继保类，无法细分保护类型 |

**阶段 B 实际可 KB 接地的只有 `standard_series`（按 standard_no 前缀聚合）**。其余维度在 `voltage_level` 字段被实际填充之前均为 LLM 生成。

完整流程（单次 LLM 调用）：

```
第一次（也是唯一一次）LLM 调用
  输入：标准化后的查询
  输出：vagueness_score + strategy + missing_dimensions（枚举key）
        + options 初始值（LLM 生成，含幻觉风险）
        + lane + lane_confidence + lane_reason
  ↓
对 missing_dimensions 中可 KB 聚合的维度（当前仅 standard_series）：
  ES 聚合真实 standard_no → 替换 options 中对应项的 standard_preview 和 doc_count
对其余不可聚合的维度：
  保留 LLM 生成的 options，前端标注"仅供参考"
  ↓
返回预处理结果
```

## 四、交互模式设计

### 4.1 新旧交互对比

| 维度 | 当前（阶段 A） | 阶段 B |
|------|--------------|--------|
| 请求次数（清晰查询） | 1 次（直接召回） | 2 次（预处理 + 召回） |
| 请求次数（笼统查询） | 2 次（触发澄清返回 400 + 澄清后重请求） | 2 次（预处理返回 200 + 确认后召回） |
| 第一次请求 HTTP 状态 | 笼统时 400，清晰时直接 200 召回 | 始终 200，返回预处理结果 |
| 路由对用户可见 | 否 | 是 |
| 用户修改路由 | 不支持 | 支持（切换按钮） |
| 澄清时机 | 提交前阻断（400 响应） | 展示确认面板，非阻断 |
| 严重笼统查询 | 弹窗强制澄清 | 仍可提交，但展示警示文本 |

### 4.2 严重笼统查询的处理

当 `vagueness_score > 0.8` 时，不再弹窗阻断，改为前端在输入框下方展示一条警示：

```
⚠ 查询较笼统，可能影响回答质量。建议补充：电压等级、设备类型
```

澄清选项仍然展示，但用户可以忽略直接提交。这样避免了阻断体验，同时保留了引导功能。

## 五、API 变更

阶段 B 将原来的单一 `POST /api/v1/query` 拆为两次调用，对应两次请求：

### 5.1 第一次请求：预处理（新增端点）

```
POST /api/v1/query/preprocess
```

**请求体**（复用现有 `QueryRequest`，无需修改）：
```json
{ "query": "隔离开关安全距离" }
```

**响应体**（新增 `PreprocessResponse`，始终 200）：
```json
{
  "normalized_query": "隔离开关安全距离",
  "vagueness_score": 0.65,
  "strategy": "clarify_optional",
  "missing_dimensions": ["voltage_level"],
  "options": [
    {
      "id": 1,
      "label": "10kV户内隔离开关",
      "refined_query": "10kV户内隔离开关安全净距要求",
      "standard_preview": "GB 1985-2004",
      "doc_count": 23,
      "kb_verified": true
    },
    {
      "id": 2,
      "label": "35kV户外隔离开关",
      "refined_query": "35kV户外隔离开关安全净距要求",
      "standard_preview": null,
      "doc_count": null,
      "kb_verified": false
    }
  ],
  "lane_suggestion": {
    "lane": "fast",
    "confidence": 0.82,
    "reason": "单一维度查询，包含具体设备类型，无对比或多跳需求"
  }
}
```

`kb_verified: true` 表示该选项的 `standard_preview` 和 `doc_count` 来自 ES 真实聚合；`false` 表示 LLM 生成，前端应标注"仅供参考"。

> **层次说明**：`lane_suggestion` 由 `QueryOptimizer`（预处理层）输出，是大模型的路由建议，不是最终决策。最终路由决策仍由第二次请求中的 `Router`（路由层）执行，`user_lane` 只在 `QueryService` 层覆盖 Router 的输出。这符合 `08-RAG功能层次与状态机.md` 的分层约束。

### 5.2 第二次请求：执行查询（在现有端点上扩展）

```
POST /api/v1/query
```

在现有 `QueryRequest` 基础上新增字段：

```json
{
  "query": "隔离开关安全距离",
  "refined_query": "10kV户内隔离开关安全净距要求",
  "selected_option_id": 1,
  "user_lane": "fast",
  "clarification_context": {
    "vagueness_score": 0.65,
    "strategy": "clarify_optional",
    "missing_dimensions": ["voltage_level"],
    "options": [...]
  }
}
```

新增字段：

| 字段 | 类型 | 说明 |
|------|------|------|
| `user_lane` | `"fast" \| "slow" \| null` | 用户选择的车道；null 表示接受 `lane_suggestion` |

**`QueryService` 路由决策逻辑**（优先级从高到低）：
1. `user_lane` 不为 null → 直接使用，跳过 Router 输出
2. `user_lane` 为 null → 使用 Router 的规则路由结果
3. Router 出错 → 回退到 `lane_suggestion.lane`

## 六、日志与缓存变更

### 6.1 query_logs 表扩展

`06-数据模型设计.md` 中 `query_logs.lane` 已定义为 `ENUM('fast', 'slow') NOT NULL`，含义为"最终实际使用的车道"。阶段 B 新增两个字段，三者关系如下：

| 字段 | 类型约束 | 含义 | 写入逻辑 |
|------|---------|------|---------|
| `predicted_lane` | VARCHAR(10) NOT NULL | LLM 建议的车道 | 始终写入，来自 `lane_suggestion.lane` |
| `user_lane` | VARCHAR(10) NULL | 用户覆盖的车道 | 仅当用户修改了建议时写入，否则为 NULL |
| `lane`（已有） | ENUM NOT NULL | 最终实际使用的车道 | `user_lane IS NOT NULL ? user_lane : router_result` |

`lane` 字段的写入逻辑从"Router 输出"改为"Router 输出，但 `user_lane` 不为 null 时覆盖"。

新增的两个字段：

| 字段 | 类型约束 | 说明 |
|------|---------|------|
| `predicted_lane` | VARCHAR(10) NOT NULL | LLM 建议的车道，来自 `lane_suggestion.lane`，始终写入 |
| `lane_confidence` | FLOAT | 路由置信度，来自 `lane_suggestion.confidence` |
| `user_lane` | VARCHAR(10) NULL | 用户实际选择的车道，NULL 表示接受建议 |

**核心训练信号**：`predicted_lane != lane` 的记录即为路由误判样本（用户修改或 Router 覆盖了 LLM 建议），无需人工标注。

数据飞轮中各用户行为的标注含义：

| 用户行为 | 标注含义 |
|---------|---------|
| `user_lane IS NULL`（接受建议） | 路由正样本 |
| `user_lane = "slow"`（从 fast 改为 slow） | fast 负样本 |
| `user_lane = "fast"`（从 slow 改为 fast） | slow 负样本 |
| 选择澄清选项 | `missing_dimensions` 正样本 |
| 跳过澄清选项 | `vagueness_score` 偏高，建议下调 |

### 6.2 Redis 缓存结构同步更新

`06-数据模型设计.md` 中预处理缓存 key 为 `vagueness:hot:{query_hash}`，存储值仅包含旧字段：

```json
{
  "vagueness_score": 0.75,
  "strategy": "clarify_optional",
  "missing_dimensions": ["voltage_level"],
  "cached_at": 1704556800
}
```

阶段 B 上线时需同步更新缓存值结构，增加路由相关字段：

```json
{
  "vagueness_score": 0.75,
  "strategy": "clarify_optional",
  "missing_dimensions": ["voltage_level"],
  "options": [...],
  "lane_suggestion": {
    "lane": "fast",
    "confidence": 0.82,
    "reason": "..."
  },
  "cached_at": 1704556800
}
```

**上线操作**：阶段 B 部署前需执行 `DEL vagueness:hot:*` 和 `DEL vagueness:warm:*` 清除旧格式缓存，否则命中旧缓存的请求不会返回 `lane_suggestion`，前端面板无法渲染。

## 七、实施步骤

### Step 1：扩展一体化 LLM 调用，输出路由建议

修改 `query_optimizer.py` 中的 `_llm_optimize()` prompt，要求同时输出 `lane`、`lane_confidence`、`lane_reason`。

验收标准：单元测试覆盖 5 个典型案例（明确标准号、对比查询、多跳推理、单维度、严重笼统），路由建议与人工预期一致。

### Step 2：澄清维度改为枚举 + KB 聚合填值

- 定义 `POWER_CLARIFICATION_DIMS` 常量
- 修改 prompt，要求 `missing_dimensions` 从枚举 key 中选择，同时在第一次 LLM 调用中直接生成 `options` 初始值
- 实现 `search_engine.aggregate_by_standard(query)` ES 聚合接口，按 `standard_no` 前缀分组
- 对 `missing_dimensions` 中含 `standard_series` 的选项，用聚合结果替换 `standard_preview` 和 `doc_count`，并标记 `kb_verified: true`
- 其余维度的选项保持 LLM 生成，标记 `kb_verified: false`

验收标准：`kb_verified: true` 的选项标准号可在 ES 中查到且文档数量与实际一致；`kb_verified: false` 的选项前端正确标注"仅供参考"。

### Step 3：API 端点与 Schema 变更

- 新增 `POST /api/v1/query/preprocess` 端点，返回 `PreprocessResponse`（含 `lane_suggestion`）
- `QueryRequest` 新增 `user_lane` 字段
- `QueryService` 路由决策逻辑（优先级见第五节）：`user_lane` 不为 null 时覆盖 Router 结果；Router 出错时回退到 `lane_suggestion.lane`

### Step 4：日志表扩展

- `query_logs` 新增 `predicted_lane`（NOT NULL）、`lane_confidence`、`user_lane`（NULL）三个字段
- 更新 `lane` 字段的写入逻辑：由 `QueryService` 在 Router 执行后，判断 `user_lane` 是否不为 null，是则用 `user_lane` 覆盖 Router 结果后写入 `lane`
- 服务层在记录日志时同时写入 `predicted_lane`（来自 `lane_suggestion`）和 `user_lane`（来自请求体）

### Step 5：Redis 缓存清理

- 更新 `vagueness:hot:*` 和 `vagueness:warm:*` 的缓存值结构（见第六节）
- 部署前执行 `DEL vagueness:hot:*` 和 `DEL vagueness:warm:*`，清除旧格式缓存

### Step 6：历史数据兼容

`clarification_logs.missing_dimensions` 历史记录存储的是中文自由文本（如 `["电压等级", "应用场景"]`），阶段 B 改为枚举 key（如 `["voltage_level", "application_scene"]`）。两种格式共存会导致 Loop Engineering 的分析 SQL 失效。

处理方式：编写一次性迁移脚本，将历史记录中的中文文本映射为枚举 key，未能匹配的条目写入 `null` 并保留原始值到 `missing_dimensions_raw` 备用字段（可选）。

迁移可在阶段 B 上线后异步执行，不阻塞上线。

### Step 7：前端集成

- 新增对 `POST /api/v1/query/preprocess` 的调用，在输入框提交后展示预处理结果面板
- 面板展示：路由建议（带切换按钮）+ 澄清选项（`kb_verified=false` 的标注"仅供参考"）
- 严重笼统时（`vagueness_score > 0.8`）展示警示文本而非弹窗
- 用户确认后调用 `POST /api/v1/query`，携带 `user_lane` 和选中的 `refined_query`
- 对于置信度高（`lane_confidence > 0.85`）且笼统度低（`vagueness_score < 0.3`）的查询，前端可跳过面板直接自动提交第二次请求，用户感知仍是一次交互

## 八、成功标准

阶段 B 运行 4-6 周后，用以下指标评估是否达到预期，以及是否具备进入阶段 C 的条件：

| 指标 | 目标 | 说明 |
|------|------|------|
| 训练数据积累量 | ≥ 1000 条有效记录 | `query_logs` 中 `predicted_lane` 不为 NULL |
| 路由修改率 | < 15% | 过高说明大模型路由质量不够，阶段 C 的训练数据噪声大 |
| 澄清选项接受率 | ≥ 40% | 低于此值说明 KB 引导效果不好，需先优化选项质量 |
| 端到端延迟 P99 | < 5s | 相比当前（笼统查询两次请求）有改善 |

路由修改率若持续 > 30%，说明大模型在该领域路由能力不足，需评估是否补充 few-shot 示例或提前进入阶段 C。
