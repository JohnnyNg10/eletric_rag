## 二、根因分析

### 根因 #1：二次重排对完全相同的 43 个 chunk 重复计算（最严重）

**现象**：

- 首轮召回（过滤放宽后）得到 43 个 chunk
- 充分性判断失败，触发 retry
- Retry 召回返回 **0 个新 chunk**
- 6 个被引用标准也全部返回 **0 结果**
- 合并去重后 merged_chunks 与首轮 deduped_chunks **完全相同（43 个）**
- 但代码仍对这 43 个 chunk 执行了完整的二次粗排 + 二次精排
- 二次重排耗时 **41,800ms**，是完全无效计算

**代码位置**：`backend/app/core/retrieval/fast_lane.py:240-244`

```python
# 当前实现——直接调用 rerank，未检测是否有新 chunk
reranked_results = await self.reranker.rerank(
    query=query,
    candidates=merged_chunks,
    top_k=10
)
```

此处没有调用 `cache.get_rerank()`，跳过了 L3 重排缓存，而首轮已将相同 query + chunk_ids 写入缓存。

---

### 根因 #2：重排器在 CPU 上运行，无量化加速

**现象**：
- 粗排（bge-reranker-base）处理 43 个 chunk 需要 15–20s
- 精排（bge-reranker-large）处理 20 个 chunk 需要 21–22s
- 代码使用 `torch.no_grad()` + FP32 CPU 推理，无 GPU、无量化

**代码位置**：`backend/app/core/retrieval/rerank.py:379`

```python
with torch.no_grad():
    outputs = model(**inputs)
```

`torch.no_grad()` 不禁用 autograd 的内存分配，改用 `torch.inference_mode()` 可减少约 5–10% 的推理开销。更大的节省来自量化或换轻量模型。

**根因 #2.1：chunk 级缓存 key 格式不匹配（已修复）**✅

**问题**：`rerank.py` 的 `_compute_scores()` 方法中，chunk 级缓存读取 key 包含 `stage` 和 `model_version`，但写入 key 缺失这两个字段，导致缓存永远无法命中。

**修复位置**：`backend/app/core/retrieval/rerank.py:392`

修复前（缓存 key 不匹配）：
```python
# 读 key（line 351，包含 stage + model_version）
cache_key = f"rerank:score:{stage}:{model_version}:{query_hash}:{candidate.chunk_id}"

# 写 key（line 392，缺失 stage + model_version）
cache_key = f"rerank:score:{query_hash}:{batch[idx].chunk_id}"  # ❌ 格式不匹配
```

修复后（格式对齐）：
```python
# 写 key（line 392，已修复）
cache_key = f"rerank:score:{stage}:{model_version}:{query_hash}:{batch[idx].chunk_id}"  # ✅
```

**实施状态**：✅ 已完成（2026-07-16）

**收益**：当 retry 路径对相同 chunk 集重新重排时，老 chunk 的分数直接从 chunk 级缓存读取，只有新 chunk 需要推理。结合方案 A 的 `new_in_retry` 检测，双重避免重复计算。

---

### 根因 #3：首轮召回因 category 过滤命中 0 结果，浪费 7s

**现象**：

```
[VectorRecall] DONE found=0    # 带 category='继保' 过滤
[KeywordRecall] DONE found=0   # 带 category='继保' 过滤
[StructuredRecall] Found 0 results
→ Filter relaxation triggered，去掉过滤后第二次召回成功（564ms）
```

数据库中没有 `category='继保'` 的文档（或分类与 LLM 识别的标签不一致），导致首轮召回必然失败，额外消耗 ~7s，且这一情况每次该类查询都会重现。

---

### 根因 #4：二次充分性判断无意义（相同数据集）

**现象**：

- 二次重排后的 10 个 chunk 与首轮 8 个 chunk 来自同一 43 个候选
- 充分性 LLM 调用两次，confidence 从 0.90 降到 0.60
- 第二次判断额外消耗 7,300ms，结果更差而非更好

根本原因：retry 没有带来任何新信息，对相同数据集判断两次是无效 LLM 消耗。

---

### 根因 #5：被引用标准召回是顺序 DB 查询

**现象**：

```
[FastLane] Detected referenced standards: ['DL 584', 'GB/T 13955', 'DL/T 5198', 'GB/T 14285', 'GB 50054', 'DL/T 584', 'GB/T 33982']
```

7 个标准（含重复的 DL/T 584 / DL 584）逐一顺序查询 MySQL，且全部返回 0。
代码位置：`fast_lane.py:562-574`，使用 `for standard_no in standard_nos:` 串行循环。

**根因 #6：首次 HTTP 请求触发模型加载（已修复）**✅

**问题**：reranker 模型（bge-reranker-base + bge-reranker-large，合计 ~2.6GB）在首次 HTTP 请求时才加载到内存，首次查询延迟增加 5–10s。

**根因**：`main.py` 的 `startup_event()` 只调用 `init_models()`（检查文件是否存在），未调用 `get_reranker()` 加载模型权重到内存。

**修复位置**：`backend/app/main.py:72-79`

修复内容：
```python
# 3. 预加载重排模型（避免首次请求承担模型加载延迟）
logger.info("Step 3/3: Warming up reranker models...")
try:
    from app.core.retrieval.rerank import get_reranker
    get_reranker()
    logger.info("Reranker models loaded successfully")
except Exception as e:
    logger.warning(f"Reranker warmup failed (non-fatal): {e}")
```

**实施状态**：✅ 已完成（2026-07-16）

**收益**：首次 HTTP 请求无需等待模型加载，节省 5–10s 首查询延迟。后续所有请求共享已加载的模型单例（`_reranker_instance`）。

## 三、优化方案

### 方案 A（P0 - 消除二次重排，预期节省 ~42s）✅ 已实施

**在 retry 路径中检测 merged_chunks 是否有新增，无新增则复用首轮重排结果。**

**实施状态**：✅ 已完成（2026-07-16）

修改位置：`backend/app/core/retrieval/fast_lane.py:239-276`

**实施内容**：

1. **新 chunk 检测逻辑**（line 240-241）：
```python
original_ids = {c.chunk_id for c in deduped_chunks}
new_in_retry = [c for c in merged_chunks if c.chunk_id not in original_ids]
```

2. **无新 chunk 时跳过重排**（line 243-245）：
```python
if not new_in_retry:
    logger.info("[FastLane] Retry brought no new chunks, reusing first-pass rerank results")
    reranked_results = reranked_results[:10]
```

3. **有新 chunk 时走 L3 缓存 + reranker**（line 247-261）：
```python
else:
    logger.info(f"[FastLane] Retry brought {len(new_in_retry)} new chunks, re-ranking merged set")
    retry_chunk_ids = [c.chunk_id for c in merged_chunks]
    cached_retry_rerank = cache.get_rerank(query, retry_chunk_ids)
    if cached_retry_rerank is not None:
        logger.info("[FastLane] L3 retry rerank cache hit")
        reranked_results = [RerankResult(**r) for r in cached_retry_rerank]
    else:
        reranked_results = await self.reranker.rerank(
            query=query, candidates=merged_chunks, top_k=10
        )
        cache.set_rerank(query, retry_chunk_ids, [asdict(r) for r in reranked_results])
```

4. **有新 chunk 时才执行二次充分性判断**（line 268-275）：
```python
if len(reranked_results) > 0:
    logger.info(f"[FastLane] Re-checking sufficiency after retry with {len(reranked_results)} results")
    retry_sufficiency_result = await self.sufficiency_checker.check(...)
    sufficiency_result = retry_sufficiency_result
```

**实际收益**：当 retry 无新 chunk 时节省 **~49,100ms（二次重排 41,800ms + 二次充分性 7,300ms）**。

**附加优化**：修复了 L3 缓存在 retry 路径的写入逻辑，有新 chunk 时也会写入缓存供后续查询使用。

### 方案 B（P0 - 修复 category 过滤始终失败的问题，节省 ~7s）

**问题**：LLM 将查询分类为"继保"，但数据库文档的 `category` 字段值不匹配（可能是"保护"、"继电保护"等变体）。

**排查步骤**：

```sql
-- 查看数据库中实际使用的 category 值
SELECT DISTINCT category, COUNT(*) as cnt
FROM documents
WHERE status = 'valid'
GROUP BY category
ORDER BY cnt DESC;
```

**修复方向**（选其一）：

1. **统一 category 枚举**：在文档入库时规范化 category 为固定枚举集，与 LLM 分类结果保持一致。
2. **模糊匹配过滤**：将 ES filter 的 `{"term": {"category": "继保"}}` 改为 `{"match": {"category": "继保"}}`，允许相似词命中。
3. **category 别名映射**：在 MetadataExtractor 中维护一个映射表，将 LLM 输出的类别标签映射到数据库实际值。

**预期收益**：消除首轮召回必然失败的开销，节省 **~7,000ms**。

### 方案 C（P1 - 并行被引用标准召回，节省 ~100ms）

**将顺序 for 循环改为 `asyncio.gather`：**

```python
# fast_lane.py:_recall_referenced_standards()
# 原实现：
for standard_no in standard_nos:
    chunks = await structured_recall.search(...)
    all_chunks.extend(chunks)

# 修改为：
tasks = [
    structured_recall.search(query="", filters={"standard_no": re.sub(r'\s+', ' ', s).strip()}, top_k=10)
    for s in standard_nos
]
results = await asyncio.gather(*tasks)
for chunks in results:
    all_chunks.extend(chunks)
```

同时在进入并行召回前**去重标准号**（本次日志中 "DL 584" 和 "DL/T 584" 重复出现两次）：

```python
# reference_extractor 或 fast_lane 中去重
all_referenced_standards = list(dict.fromkeys(  # 保序去重
    re.sub(r'\s+', ' ', s).strip() for s in all_referenced_standards
))
```

**预期收益**：节省 **~100–200ms**（当前全 0 时效果不明显，但标准库建好后效果显著）。

### 方案 D（P1 - 重排器 CPU 推理加速）

**选项 D-1（最简单，改 1 行）**：将 `torch.no_grad()` 改为 `torch.inference_mode()`

```python
# rerank.py:379
with torch.inference_mode():   # 替换 torch.no_grad()
    outputs = model(**inputs)
```

预期收益：减少 5–10% 推理耗时（约 4–8s）。

**选项 D-2（中等改动）**：导出 ONNX，使用 ONNXRuntime CPU 推理

BGE reranker 模型导出 ONNX 后，ONNXRuntime 在 CPU 上通常比 PyTorch FP32 快 **1.5–3 倍**。粗排 + 精排合计有望从 37s 降至 **15–25s**。

参考脚本（一次性预处理，不改在线路径）：
```python
from optimum.onnxruntime import ORTModelForSequenceClassification
model = ORTModelForSequenceClassification.from_pretrained(
    model_path, export=True, provider="CPUExecutionProvider"
)
```

**选项 D-3（最大收益，需硬件）**：使用 GPU 推理

如果服务器有 GPU，将模型移至 CUDA：
```python
device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
self.coarse_model = self.coarse_model.to(device)
# inputs 也需移到 device
inputs = {k: v.to(device) for k, v in inputs.items()}
```

GPU 下粗排 + 精排合计预期 **< 3s**。

---

### 方案 E（P2 - 生成层流式输出改善体验）

生成层耗时 ~25,600ms，大部分是 LLM 首 token 延迟 + 输出时间。这部分较难压缩，但可通过**流式响应**让用户看到内容逐步输出，消除等待感。

当前 `generator.py` 使用一次性返回，修改为 `stream=True` 并通过 SSE 推送（已有 WebSocket 基础设施，改动量小）。
