# 预处理与路由阶段优化分析

> 分析范围：从用户输入查询到路由判断（fast/slow）的完整流程  
> 对应流程图：`docs/architecture/flows/16-业务流程图.md` 第一节 9-18 行  
> 撰写日期：2026-07-10

---

## 一、现状分析

### 1.1 当前流程

```
原始查询
  ↓
[术语标准化]     词典查找，规则替换，~5ms
  ↓
[笼统度评估 + 澄清选项生成]   一体化 LLM 调用，~4000ms（含选项生成）
  ↓
[用户交互]       阻断（clarify_required）或非阻断（suggest/clarify_optional）
  ↓  ← 用户选择/跳过后携带 refined_query 二次请求
[路由决策]       关键词规则，~1ms
  ↓
fast 或 slow
```

### 1.2 各模块实现状态

| 模块 | 实现方式 | 准确率 | P99 延迟 | 已知问题 |
|------|---------|--------|----------|---------|
| 术语标准化 | 词典映射（TermNormalizer） | ~95%（词典覆盖范围内） | <10ms | 词典覆盖有限，上下文无关 |
| 笼统度评估 | LLM 一体化调用（已从规则升级） | 85-90% | ~4000ms | 冷查询慢，缺知识库接地 |
| 澄清选项生成 | LLM 凭空生成（未接 KB） | 选项相关性中等 | 含在上方 | 无实际标准号/文档数量，用户跳过率高 |
| 路由决策 | 关键词规则（Router） | ~80%（覆盖显式规则的查询） | <5ms | 无法处理规则边界模糊的查询 |

**当前已完成的优化**：
- ✅ 笼统度评估从规则升级为 LLM（准确率 +25%）
- ✅ 笼统度评估与澄清选项生成合并为一次 LLM 调用（性能 +54%）
- ✅ 澄清日志记录（`query_logs` + `clarification_logs`）支持后续闭环

## 二、性能瓶颈定位

### 2.1 延迟分布（快车道路径）

```
术语标准化:       5ms
笼统度+澄清生成:  4000ms  ← 主要瓶颈（LLM 冷调用）
用户交互等待:     变量（用户行为）
路由决策:         1ms
─────────────────────────────
路由前总耗时:     ~4006ms（不含用户等待）
```

快车道端到端目标 P99 < 4s，预处理阶段本身就已逼近上限。

### 2.2 质量缺口

**1. 澄清选项缺乏知识库接地**

当前 LLM 凭空生成"10kV户内隔离开关技术参数"，但：
- 无法确认该标准是否在库
- 文档数量为假数据（用户无法判断选项价值）
- LLM 可能幻觉标准号（如"GB 1985-2015"实为"GB 1985-2004"）

**2. 路由规则覆盖不足**

路由仅靠关键词匹配：
```python
if has_explicit_standard_clause(query): return "fast"
if has_comparison_keywords(query):      return "slow"
```

边界模糊案例无规则可依：
- "10kV和35kV配电装置的接地要求区别" → 应为 slow（对比），但无"对比"关键词
- "继电保护整定和配置的关系" → 应为 slow（多维关联），规则判为 fast

**3. 领域知识依赖问题**

LLM 可以识别"缺少电压等级"这个维度类别，但无法准确给出"该库实际有 6kV/10kV/35kV/110kV" 的知识——这些信息只在运行时知识库里。

## 三、优化方向对比

### 方向 A：现有流程增量优化（不改交互模式）

在当前"澄清交互在路由之前"的架构下做局部改进。

| 优化点 | 措施 | 收益 | 难度 |
|--------|------|------|------|
| 澄清选项接 KB | ES 聚合查询实际标准 → LLM 基于真实数据生成选项 | 用户选择率从 20-30% → 60%+ | 中（需实现 ES 聚合接口） |
| 路由升级为分类器 | 积累规则误判日志 → 微调轻量分类模型 | 路由准确率从 ~80% → ~92% | 中（需标注数据 500-1000 条） |
| 清晰查询提前短路 | 规则快速检测明确标准号/条款号 → 跳过 LLM 笼统度调用 | 约 60% 的查询省掉 4s LLM | 低（规则扩展） |

**方向 A 的核心局限**：流程中仍有阻断性用户交互，无法对整段流程做端到端优化。

---

### 方向 B：路由前置（重排流程顺序）

将路由决策提前到笼统度评估之前，利用规则快速过滤：

```
原始查询
  ↓
[术语标准化]              ~5ms
  ↓
[快速规则路由]            ~1ms
  ├── 明确标准号/条款号 → fast，跳过笼统度评估，直接召回
  └── 其他 → 继续评估
  ↓
[LLM 笼统度 + 澄清]       ~4000ms（仅约 40% 的查询触发）
  ↓
[用户交互]
  ↓
[精细路由决策]
```

**收益**：约 60% 含明确标准号的查询可绕过 LLM 调用，端到端延迟降至 <500ms。  
**局限**：笼统度评估和路由仍是两个独立判断，澄清选项质量问题未解决。

---

### 方向 C：一体化判断 + 用户后确认（推荐研究方向）

改变交互模式：AI 先完成所有判断并展示结果，用户在事后确认或替换，而非在流程中间阻断等待。

**流程变为**：
```
原始查询
  ↓
[术语标准化]              ~5ms（词典，保持不变）
  ↓
[一体化 LLM / 微调模型]   ~100-500ms（目标）
  输出：{
    normalized_query,      # 标准化后的查询
    vagueness_score,        # 笼统度
    strategy,               # none/suggest/clarify_optional/clarify_required
    missing_dimensions,     # 缺失的维度类别（非具体值）
    lane,                   # fast/slow
    lane_confidence,        # 路由置信度
    lane_reason             # 路由理由（可读）
  }
  ↓
[KB 动态填充澄清选项具体值]  ~50ms（ES 聚合查询）
  ↓
[展示给用户：路由结果 + 澄清建议]
  ↓（用户确认或替换，非阻断）
[继续执行]
```

**与方向 A/B 的本质区别**：
- 用户交互从"中间阻断"变为"事后确认"
- 整个预处理→路由判断流程变为单次推理，无等待
- 用户替换路由的行为成为高质量标注数据

---

## 四、核心挑战：LLM 领域知识不足

这是方向 C 落地的最大障碍，需要拆开分析。

### 4.1 两层任务的领域依赖差异

| 子任务 | 领域依赖强度 | 原因 | 解决方案 |
|--------|------------|------|---------|
| 判断是否需要澄清 | 低 | 识别"查询缺乏约束"是通用语言能力 | LLM 直接可用 |
| 识别缺失的维度类别 | 中 | 需知道电力领域的关键参数维度 | 预定义维度表 + 微调 |
| 填充维度的具体选项值 | 高 | 需知道库里实际有哪些值 | KB 运行时查询，不依赖模型 |
| 路由 fast/slow | 中 | 需理解"对比""多跳"的语义 | 微调分类器 |

### 4.2 预定义维度表方案

将"识别缺失维度"从开放生成变为多标签分类，大幅降低领域知识依赖：

```python
POWER_CLARIFICATION_DIMS = {
    "voltage_level":      "电压等级",      # 6/10/35/110/220/500kV
    "equipment_type":     "设备类型",      # 变压器/开关柜/GIS/电缆/互感器
    "application_scene":  "应用场景",      # 新建/改造/运维/验收/检修
    "neutral_grounding":  "中性点接地方式", # 直接/消弧线圈/不接地/低电阻
    "capacity_range":     "容量范围",      # <1MVA / 1-10MVA / >10MVA
    "install_env":        "安装环境",      # 户内/户外/地下/高海拔
    "standard_series":    "标准系列",      # GB/DL/NB/企标
    "protection_type":    "保护类型",      # 差动/距离/过流/零序
}
```

模型输出：`missing_dimensions: ["voltage_level", "application_scene"]`  
KB 查询：`ES.aggregate(query, group_by=["voltage_level", "category"])`  
用户看到：从库里取出的真实值（如"10kV、35kV、110kV"均有文档覆盖）

**效果**：模型不需要知道库里有哪些具体值，只需判断缺哪个维度类别。这是可训练的。

## 五、端到端微调可行性评估

### 5.1 任务定义

```
输入：术语标准化后的查询（字符串）
输出：
  {
    "vagueness_score": 0.65,
    "strategy": "clarify_optional",
    "missing_dimensions": ["voltage_level"],
    "lane": "fast",
    "lane_confidence": 0.82,
    "lane_reason": "包含具体设备类型，单维度查询"
  }
```

### 5.2 可行性判断

| 维度 | 评估 |
|------|------|
| 任务结构清晰度 | ✅ 固定输入输出格式，适合监督微调 |
| 子任务相关性 | ✅ 笼统度高的查询（多维度不明确）更可能是 slow lane |
| 训练数据可获取性 | ✅ 已有 `clarification_logs` + `query_logs`（路由决策） |
| 推理速度目标 | ✅ 7B 量级模型推理 <200ms，显著低于当前 4000ms |
| 领域知识依赖 | ⚠️ 需配合预定义维度表降低依赖 |

**结论**：技术上可行。前提是积累足够标注数据（建议冷启动阶段先用大模型收集，达到 1000+ 条后启动微调）。

### 5.3 推荐的冷启动路径

```
阶段0（现在）：
  当前一体化 LLM 方案（豆包/通义）
  记录 clarification_logs、query_logs
  ↓（积累 500 条）
阶段1（~1个月后）：
  接入 ES 知识库，澄清选项从"凭空生成"改为"KB 引导"
  用户接受率提升，日志质量提高
  ↓（积累 1000-2000 条）
阶段2（~3个月后）：
  用日志标注 {vagueness_score, missing_dimensions, lane} 三元组
  微调 Qwen2.5-7B 或 GLM-4-9B
  A/B 测试：微调模型 vs 当前 LLM
  ↓（验证效果后）
阶段3：
  微调模型上线，替换当前 LLM 调用
  延迟从 4000ms → 100-200ms
  成本从 ~0.001元/次 → 本地推理
```

## 六、数据飞轮设计

用户在"后确认"模式下的每次操作都是标注信号：

| 用户行为 | 信号含义 | 用于训练 |
|---------|---------|---------|
| 接受路由结果（fast）直接提交 | 路由正确 | fast 正样本 |
| 将 fast 改为 slow 再提交 | 路由误判 | fast 负样本 / slow 正样本 |
| 选择一个澄清选项 | 该维度判断正确 | missing_dim 正样本 |
| 跳过所有澄清建议 | 笼统度可能误判（偏高） | vagueness 分数应下调 |
| 自定义输入替换系统建议 | 系统建议的维度值不准 | KB 聚合质量问题（非模型问题） |

### 数据采集 SQL

```sql
-- 路由误判样本（用户主动修改了路由）
SELECT
    q.original_query,
    q.normalized_query,
    q.lane           AS model_predicted,
    q.user_lane      AS user_corrected   -- 需新增字段
FROM query_logs q
WHERE q.user_lane IS NOT NULL
  AND q.user_lane != q.lane;

-- 笼统度过高误判（用户跳过了系统建议的澄清）
SELECT
    c.original_query,
    c.vagueness_score AS model_score,
    0.2               AS corrected_score  -- 用户跳过 = 实际不需要澄清
FROM clarification_logs c
WHERE c.user_choice = 'skip'
GROUP BY c.original_query
HAVING COUNT(*) >= 3;  -- 同一查询被多次跳过

-- 高质量正样本（用户选择了澄清选项，后续检索成功）
SELECT
    c.original_query,
    c.vagueness_score,
    c.missing_dimensions,
    q.lane,
    q.retrieval_success
FROM clarification_logs c
JOIN query_logs q ON c.query_log_id = q.id
WHERE c.user_choice LIKE 'option_%'
  AND q.retrieval_success = TRUE;
```

## 七、推荐实施路线图

### 近期（1-2 周）：无需改架构，立即收益

1. **接入 ES 知识库生成澄清选项**（方向 A 优先项）
   - 实现 `search_engine.aggregate_by_standard(query, top_n=10)`
   - LLM 基于真实标准清单生成选项（而非凭空生成）
   - 预期：澄清选项相关性显著提升，用户跳过率下降

2. **清晰查询提前短路**（方向 B 的快速实现）
   - 在笼统度评估前先做正则检测：含 `GB/DL/NB \d+-\d+` 格式 → 直接路由
   - 约 60% 的精确查询跳过 4s LLM 调用
   - 预期：这类查询延迟从 ~4s → <20ms

3. **新增 `user_lane` 字段到 `query_logs`**
   - 为后续数据飞轮准备，记录用户实际选择的车道（如果修改了默认值）

### 中期（1-3 个月）：引入后确认交互模式

4. **将 `lane` 和 `lane_reason` 加入预处理响应**
   - 一体化 LLM 调用同时输出路由建议（目前只输出笼统度）
   - 前端展示"系统建议：快车道，因为XX"，用户可一键切换
   - 开始积累路由反馈数据

5. **预定义维度表落地**
   - 定义 `POWER_CLARIFICATION_DIMS`（约 8-12 个维度）
   - 将 `missing_dimensions` 从自由文本改为枚举值
   - 提高数据标注的一致性

### 长期（3-6 个月）：微调小模型替换大模型

6. **标注 1000-2000 条训练数据**
   - 从日志自动提取（用户信号）+ 人工审核
   - 三元组：`{query → vagueness_score, missing_dims, lane}`

7. **微调轻量模型**
   - 基座：Qwen2.5-7B-Instruct 或 GLM-4-9B
   - 训练目标：多任务输出（回归 + 多标签分类 + 二分类）
   - 推理部署：vLLM 或 llama.cpp，本地 GPU

8. **A/B 测试验证**
   - 10% 流量走微调模型，90% 走当前 LLM
   - 对比：延迟、路由准确率、用户跳过率
   - 显著优于基准（>5%）后全量切换

## 八、各方案效果预期

| 阶段 | 方案 | 预处理延迟 P99 | 路由准确率 | 用户澄清接受率 |
|------|------|--------------|----------|--------------|
| 当前 | 规则 + LLM | ~4000ms | ~80% | 20-30% |
| 近期 A | KB 接地 + 短路 | ~500ms（清晰查询）/ ~4000ms（笼统查询） | ~80% | 60%+ |
| 中期 B | 一体化输出 + 后确认 | ~4200ms（+路由判断 200ms）| ~85% | 60%+ |
| 长期 C | 微调模型 | ~150ms | ~90%+ | 60%+ |

## 九、风险与约束

| 风险 | 影响 | 缓解 |
|------|------|------|
| 澄清选项从"阻断"改为"后确认"，部分场景失去引导价值 | 严重笼统查询（score>0.8）召回质量可能下降 | 对 score>0.8 的查询仍保留阻断澄清，其余改为后确认 |
| 微调数据不足，模型泛化差 | 路由准确率不如大模型 | A/B 测试把关，不足时继续用大模型 |
| 预定义维度表覆盖不完整 | 漏掉某些领域特有维度 | 维度表开放扩展，通过日志中的用户自定义输入发现新维度 |
| 后确认模式增加前端复杂度 | 开发工期 | 可先做只读展示（不可修改），后续再加编辑入口 |
