# 重排层设计

## 1. 概述

### 1.1 定位

重排层（Reranking Layer）是 RAG 系统检索引擎的第二级，接收召回层返回的 Top50 候选块，通过两阶段精细化排序将其压缩到 Top5，并通过充分性判断决定是否触发二次检索。

重排层的核心原则：**精而准**，宁可送入生成层的块少，也要保证每一个块都高度相关。

### 1.2 在 RAG 流水线中的位置

```
预处理层 → 路由层 → 召回层（Top50）→ [重排层] → 生成层
                                          ↑
                              快车道固定流水线经过此层
                              慢车道工具循环每步不经过此层
```

**对应状态机**（`08-RAG功能层次与状态机.md`）：

```
RECALLING（召回层输出 Top50）
  ↓
RERANKING（粗排 Top50→Top20，精排 Top20→Top5）
  ↓
SUFFICIENCY_CHECK（充分性判断）
  ↓(充分)            ↓(不充分)
GENERATING      RETRY_RECALL → 重新精排 → GENERATING
```

### 1.3 核心职责

1. **粗排**：用轻量级模型将 Top50 快速压缩到 Top20，降低精排计算量
2. **精排**：用重量级模型对 Top20 深度评分，输出 Top5
3. **充分性判断**：评估 Top5 是否包含足够信息回答用户问题
4. **二次检索**：充分性不足时改写查询并触发补救召回（最多 1 次）

## 2. 两阶段重排策略

### 2.1 设计动机

召回层返回 Top50 候选块，直接全部送入精排模型成本过高（bge-reranker-large 推理慢）。两阶段策略用轻量模型先剪枝，再用重量模型精排，兼顾效率与质量。

```
召回层 Top50
    ↓
[粗排] bge-reranker-base（快，轻量）
    → Top20
    ↓
[精排] bge-reranker-large（慢，精准）
    → Top5
    ↓
充分性判断
```

### 2.2 粗排（Top50 → Top20）

| 属性 | 值 |
|------|-----|
| 模型 | `bge-reranker-base` |
| 架构 | Cross-Encoder（query + chunk 拼接后单次打分） |
| 输入 | 原始查询 + 50 个候选块文本 |
| 输出 | 50 个原始 logit 分数 |
| 归一化 | sigmoid 映射到 [0, 1] |
| 截断 | 保留 score ≥ 粗排阈值（默认 0.3）的前 20 名 |
| 延迟目标 | P50 ≤ 200 ms / P99 ≤ 400 ms（批量推理，batch_size=16，见 §7.1） |

**Cross-Encoder 与 Bi-Encoder 的区别**：召回层的向量检索用 Bi-Encoder（query 和 doc 分别编码），速度快但精度低；重排用 Cross-Encoder（query+doc 拼接），注意力可跨越两段，精度高但只能逐对打分。

### 2.3 精排（Top20 → Top5）

| 属性 | 值 |
|------|-----|
| 模型 | `bge-reranker-large` |
| 架构 | Cross-Encoder |
| 输入 | 原始查询 + 20 个粗排候选块文本 |
| 输出 | 20 个 sigmoid 归一化分数 |
| 截断 | 保留前 5 名，且 score ≥ 精排阈值（默认 0.5） |
| 延迟目标 | P50 ≤ 400 ms / P99 ≤ 800 ms（batch_size=8，见 §7.1） |

**分数融合**：精排阶段不再混合召回分数，完全依赖 bge-reranker-large 的输出分数排序。召回分数（BM25、余弦相似度）只在粗排截断时作为 tie-breaker。

### 2.4 降级策略

| 情形 | 行为 |
|------|------|
| `bge-reranker-large` 不可用 | 降级为 bge-reranker-base 执行精排 |
| `bge-reranker-base` 不可用 | 跳过两阶段重排，直接按召回分数取 Top5 |
| 候选块 < 5 | 全部通过，不触发阈值截断 |

## 3. 充分性判断

### 3.1 职责定位

充分性判断在精排之后运行，回答一个问题：**Top5 块是否已经包含足够信息来回答用户问题？**

若充分 → 直接进入生成层；若不充分 → 触发二次检索（见第 4 节），最多触发 1 次。

```
精排 Top5
    ↓
充分性判断
    ├─ 充分 → GENERATING
    └─ 不充分 → RETRY_RECALL（最多 1 次）→ 重新精排 → GENERATING
```

### 3.2 双重判断机制

充分性判断采用"规则优先、LLM 兜底"的双重机制：

**第一关：规则判断（快速路径）**

| 规则 | 阈值 | 说明 |
|------|------|------|
| 最高分过滤 | 精排 Top1 分数 ≥ 0.6 | 若最相关块分数过低，直接判不充分 |
| 覆盖度过滤 | Top5 中 score ≥ 0.5 的块数 ≥ 2 | 至少两个高相关块才算充分 |
| 空结果过滤 | Top5 非空 | 若精排后 0 结果，直接不充分 |

三条规则全部通过才进入 LLM 判断，否则直接标记"不充分"。

**第二关：LLM 充分性评估（精准路径）**

| 属性 | 值 |
|------|-----|
| 模型 | 豆包 Pro（与生成层共用 LLM 客户端） |
| 输入 | 用户原始问题 + Top5 块的文本摘要（每块截断至 200 字） |
| 输出 | JSON：`{"sufficient": true/false, "confidence": 0.0-1.0, "gaps": ["缺少X信息"]}` |
| 延迟目标 | ≤ 800 ms |
| 超时降级 | LLM 超时则默认"充分"，避免阻塞 |

**最终判定**：

```python
if not rule_check_passed:
    return SufficiencyResult(sufficient=False, source="rule", confidence=0.0, gaps=[])

try:
    llm_result = await llm_judge(query, top_results)
except asyncio.TimeoutError:
    return SufficiencyResult(sufficient=True, source="timeout_fallback", confidence=0.0, gaps=[])

if llm_result.sufficient and llm_result.confidence >= 0.7:
    return SufficiencyResult(sufficient=True, source="llm", confidence=llm_result.confidence, gaps=[])
return SufficiencyResult(sufficient=False, source="llm", confidence=llm_result.confidence, gaps=llm_result.gaps)
```

### 3.3 状态写入

充分性判断结果写入 `query_logs.sufficiency_result`（JSON 列），格式：

```json
{
  "sufficient": false,
  "source": "llm",
  "confidence": 0.45,
  "gaps": ["缺少低压配电盘的具体接线规范"]
}
```

## 4. 二次检索

### 4.1 触发条件

充分性判断返回 `sufficient=False` 且本次查询尚未执行过二次检索（`retry_count == 0`）时触发。每个查询最多触发 **1 次**二次检索，防止无限循环。

### 4.2 缺口分析与查询改写

二次检索不重复原查询，而是基于 LLM 返回的 `gaps` 字段改写查询：

| 步骤 | 操作 |
|------|------|
| 1 | 读取充分性判断中的 `gaps` 列表 |
| 2 | 将 gaps 与原始查询组合，用 LLM 生成补充查询 |
| 3 | 生成的补充查询替换原始查询送入召回层 |

**改写提示词示意**：
```
原始问题：{query}
已有信息覆盖：{top5_summary}
信息缺口：{gaps}
请生成一个针对信息缺口的补充检索查询（不超过30字）：
```

### 4.3 补充召回与合并

| 步骤 | 说明 |
|------|------|
| 触发三路召回 | 用改写后的查询执行完整三路召回，返回 Top50 |
| 去重合并 | 将补充召回结果与原 Top5 按 `chunk_id` 去重合并 |
| 重新精排 | 对合并后的候选集（≤ 55 块）重新执行精排 |
| 截断输出 | 取精排后 Top8（比正常流程多 3 个，弥补信息缺口） |

二次检索后不再执行充分性判断，直接进入生成层，以 Top8 作为上下文。

### 4.4 状态流转

```
SUFFICIENCY_CHECK（不充分）
    ↓
RETRY_RECALL（改写查询 + 三路召回 Top50）
    ↓
RERANKING（重新精排 → Top8）
    ↓
GENERATING
```

`query_logs.retry_count` 从 0 累加到 1；补充查询追加写入 `query_logs.expanded_queries`（JSON 数组末尾）。

## 5. 数据库集成

### 5.1 读取字段（chunks / documents）

重排层从召回层接收 `RecallResult` 对象，不直接查 DB。各字段来源于召回阶段的 DB 查询结果：

| 字段 | 表.列 | 用途 |
|------|----|------|
| `chunk_id` | `chunks.id` | 去重、结果标识 |
| `content` | `chunks.content` | 送入 Cross-Encoder 打分 |
| `document_id` | `chunks.document_id` | 关联文档 |
| `standard_no` | `documents.standard_no` | 生成层引用标注 |
| `title` | `documents.title` | 生成层引用标注 |
| `clause` | `chunks.clause` | 条款级别引用 |

### 5.2 写入字段（query_logs）

每次重排完成后，将结果写入 `query_logs` 表（`db/models.py::QueryLog`）：

| 字段 | 类型 | 写入时机 | 状态 | 内容 |
|------|------|----------|------|------|
| `retry_count` | INT | 二次检索后 | 已有 | 0 或 1 |
| `retrieved_chunk_ids` | JSON | 精排完成后 | 已有（复用） | Top5/Top8 的 chunk_id 列表（与召回阶段共用） |
| `retrieval_time` | INT | 精排完成后 | 已有（复用） | 检索阶段总耗时 ms（含重排） |
| `expanded_queries` | JSON | 二次检索后 | 已有（复用） | 追加补充查询到数组末尾 |
| `rerank_scores` | JSON | 精排完成后 | 已新增 | Top5/Top8 的 chunk_id + score 列表 |
| `sufficiency_result` | JSON | 充分性判断后 | 已新增 | `{sufficient, source, confidence, gaps}` |

> `rerank_scores` 和 `sufficiency_result` 已通过 `ALTER TABLE` 写入 MySQL，`db/models.py::QueryLog` 同步更新。

### 5.3 坏案例追踪（badcase_tracking）

当充分性判断为"不充分"且二次检索后仍无法满足（生成层评分低）时，写入 `badcase_tracking` 表：

| 字段 | 内容 |
|------|------|
| `query_log_id` | 关联的 query_logs.id |
| `root_cause` | `'reranking'`（ENUM：`chunking` / `embedding` / `reranking` / `missing_doc`） |
| `root_cause_detail` | 具体缺口描述（来自充分性判断的 gaps 字段） |
| `status` | `'pending'`（默认值，ENUM：`pending` / `analyzing` / `fixed` / `ignored`） |

这为后续的 Loop Engineering（通过坏案例反推补充标注）提供数据源。

## 6. 代码结构与接口

### 6.1 目录结构

```
backend/app/core/retrieval/
├── rerank.py          # TwoStageReranker（两阶段重排）
├── sufficiency.py     # SufficiencyChecker（充分性判断）
├── fast_lane.py       # 调用重排层的编排入口
└── recall.py          # 召回层（输出 RecallResult）
```

### 6.2 核心数据类

```python
@dataclass
class RerankInput:
    query: str                        # 用户原始查询（已经过预处理）
    candidates: List[RecallResult]    # 召回层返回的 Top50

@dataclass
class RerankResult:
    chunk_id: int
    content: str
    document_id: int
    standard_no: str
    clause: Optional[str]
    score: float                      # 精排模型 sigmoid 分数
    recall_source: str                # "vector" / "keyword" / "structured"

@dataclass
class SufficiencyResult:
    sufficient: bool
    source: str                       # "rule" / "llm" / "timeout_fallback"
    confidence: float
    gaps: List[str]
```

### 6.5 fast_lane.py 调用链

```python
# retrieval/fast_lane.py（编排逻辑示意）
recall_results = await recall_engine.recall(rewritten_query, metadata, top_k=50)
rerank_results = await reranker.rerank(rewritten_query, recall_results, top_k=5)
suf = await sufficiency_checker.check(rewritten_query, rerank_results)

if not suf.sufficient and retry_count == 0:
    # 触发二次检索
    retry_query = await query_rewriter.rewrite_for_gaps(rewritten_query, suf.gaps)
    retry_recalls = await recall_engine.recall(retry_query, metadata, top_k=50)
    merged = deduplicate(rerank_results + retry_recalls)
    rerank_results = await reranker.rerank(rewritten_query, merged, top_k=8)

await log_rerank_result(query_log_id, rerank_results, suf)
```

## 7. 性能设计

### 7.1 延迟目标

| 阶段 | P50 目标 | P99 目标 |
|------|----------|----------|
| 粗排（50→20，bge-reranker-base） | ≤ 200 ms | ≤ 400 ms |
| 精排（20→5，bge-reranker-large） | ≤ 400 ms | ≤ 800 ms |
| 充分性判断（规则） | ≤ 5 ms | ≤ 10 ms |
| 充分性判断（LLM） | ≤ 600 ms | ≤ 1200 ms |
| 二次检索（含重排） | ≤ 1500 ms | ≤ 3000 ms |
| **重排层总计（首次，充分）** | **≤ 1200 ms** | **≤ 2400 ms** |

### 7.2 批量推理优化

Cross-Encoder 逐对打分成本高，批量推理是关键优化手段：

- 粗排：`batch_size=16`，50 个候选块分 4 批推理
- 精排：`batch_size=8`，20 个候选块分 3 批推理
- 文本截断：每个 chunk 最多取前 512 token（bge-reranker 的输入限制）；超长 chunk 取前 256 token 保留语义密度

### 7.3 Redis 缓存

相同 `(query, chunk_id)` 对的重排分数可缓存，TTL = 5 分钟。缓存键：

```
rerank:score:{md5(query)}:{chunk_id}
```

缓存命中时跳过模型推理，直接使用缓存分数。适用于热点问题的重复召回场景。

### 7.4 降级与超时

| 场景 | 处理 |
|------|------|
| 粗排超时（> 500 ms） | 直接用召回分数取 Top20，跳过粗排 |
| 精排超时（> 1000 ms） | 用粗排结果取 Top5 |
| LLM 充分性判断超时（> 1500 ms） | 默认充分，记录超时日志 |
| 所有重排模型不可用 | 按召回分数直接取 Top5，标记 `rerank_skipped=true` |

## 8. 重排质量评估

### 8.1 离线评估指标

使用标注数据集（`badcase_tracking` 反馈 + 人工标注的相关性标签）进行离线评估：

| 指标 | 计算方式 | 目标值 |
|------|----------|--------|
| MRR@5 | 第一个相关块的倒数排名均值 | ≥ 0.75 |
| NDCG@5 | 归一化折损累计增益，Top5 范围 | ≥ 0.70 |
| Precision@5 | Top5 中相关块比例均值 | ≥ 0.60 |
| 充分性准确率 | LLM 充分性判断与人工标注的一致率 | ≥ 0.80 |

### 8.2 在线监控指标

通过 `query_logs` 表的聚合统计，在运维面板实时展示：

| 指标 | 说明 |
|------|------|
| 充分性不足率 | `sufficiency_result.sufficient=false` 的查询比例（预期 < 20%） |
| 二次检索触发率 | `retry_count=1` 的查询比例（与充分性不足率相同） |
| 重排平均延迟 | `retrieval_time` 的 P50/P99（包含召回+重排阶段） |
| 坏案例率 | `badcase_tracking` 新增 `root_cause=reranking` 记录 / 总查询数 |

### 8.3 充分性校准

LLM 充分性判断存在误判风险（过于宽松或过于严苛）。定期抽样 100 条 `sufficient=False` 的查询，人工判断是否真的不充分，若误判率 > 20%，则调整 `confidence` 阈值或优化提示词。
