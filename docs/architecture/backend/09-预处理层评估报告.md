## 发现的问题

### 问题1: 空查询处理不当 ⚠️

**现象**：空字符串被识别为笼统查询
```python
输入: ""
输出: status='need_clarification'
```

**问题**：应该在最开始就拒绝空查询
**建议修复**：在 `Preprocessor.preprocess()` 开头添加验证

### 问题2: 同义词库有限 ⚠️

**现象**：查询改写仅限于预定义的同义词映射

**局限**：
- 无法处理同义词库外的词汇
- 无法根据上下文选择最佳同义词
- 扩展查询质量依赖人工维护词库

### 问题3: 笼统度评估基于简单规则 ⚠️

**当前规则**：
```python
- 查询长度 < 5: +0.4
- 包含笼统关键词: +0.15/个
- 缺少具体信息: +0.2
```

**局限**：
- 无法理解语义
- 误判风险（短查询未必笼统）
- 阈值硬编码，缺乏灵活性

### 问题4: 澄清选项质量低 ⚠️

**现象**：生成的澄清选项是模板化的，没有从知识库动态生成

**问题**：
- 选项通用，不够精准
- 无法提供标准预览和文档数量

## 规则 vs LLM 评估

### 当前方案：基于规则

| 组件 | 当前实现 | 优点 | 缺点 |
|------|---------|------|------|
| 术语标准化 | 词典映射 | 快速、可控 | 词典有限、上下文无关 |
| 笼统度评估 | 规则计分 | 延迟低、可解释 | 准确率有限、硬编码阈值 |
| 查询改写 | 同义词替换 | 快速、可控 | 质量一般、词库依赖 |
| 元数据提取 | 正则匹配 | 精确、快速 | 对结构化信息足够 |

### 建议：分阶段的混合方案

#### 阶段1：当前（MVP，规则为主）✅

**保持现状**，快速验证产品：
- 延迟低（P99 < 300ms）
- 成本低（无LLM调用）
- 可控、可调试
- 准确率一般（约70-80%）

#### 阶段2：混合方案（规则 + LLM）🎯 **推荐**

| 组件 | 建议 | 理由 |
|------|------|------|
| 术语标准化 | 保持规则 | 词典已足够 |
| 元数据提取 | 保持规则 | 正则已精确 |
| 笼统度评估 | **改用LLM** | 语义理解更准确 |
| 查询改写 | **改用LLM** | 质量显著提升 |
| 澄清选项 | **改用LLM+知识库** | 精准、可预览 |
