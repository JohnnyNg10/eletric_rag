## 二、关键问题诊断

### 问题 #1: 重排阶段占45%总时长 🔴

**现象:**
- 粗排: 50 chunks → 20 chunks, 耗时15秒
- 精排: 20 chunks → 8 chunks, 耗时20秒
- 总计35.3秒，占比45%

**根本原因:**
1. **模型选择**: `bge-reranker-large` (1024维) 推理速度慢
2. **串行处理**: 逐个chunk推理，未启用批量
3. **缓存未生效**: L3重排缓存代码存在但实际未命中

**影响:**
- 单次查询: +35秒
- 用户体验: 严重超时（目标<45秒，当前78秒）

---

### 问题 #2: Category过滤失败浪费9秒 ⚠️

**现象:**
- LLM预测 `category=配电`, `confidence=0.90`
- 第一轮召回强制过滤 `filters={'category': '配电'}`
- 结果: 向量0条、关键词0条、结构化0条
- 触发filter relaxation，第二轮召回（无过滤）成功返回50条

**根本原因:**
1. **知识库覆盖不足**: "配电"类别文档数量少或标注不准
2. **过滤策略过激进**: 即使confidence=0.90也强制使用must过滤
3. **无预检查机制**: 未在召回前验证category是否有文档

**影响:**
- 第一轮召回浪费: +9.1秒
- 召回路径不确定性: 有时命中、有时失败

**数据佐证:**
```log

12:04:12 - [FastLane] Low recall (0 < 3), attempting filter relaxation

12:04:12 - [MultiPathRecall] filters={}

```

---

### 问题 #3: 预处理被调用两次 ⚠️

**现象:**
- `12:03:44` - `/query/preprocess` endpoint: 3.5秒
- `12:03:51` - `query_service.execute_query` 内部: 3.5秒
- 总计7秒，且两次结果略有差异（通用 vs 配电）

**根本原因:**
前端流程设计：
1. 用户输入 → 调用 `/preprocess` → 展示澄清界面
2. 用户提交 → 调用 `/query` → 内部再次预处理

**影响:**
- 重复LLM调用: +3.5秒
- 结果不一致风险: 两次预测可能不同

---

### 问题 #4: HyDE与改写串行执行

**现象:**
```log
12:03:54 - Query decomposition: 2.6s
12:04:00 - HyDE generation: 6.6s
```

**根本原因:**
- 查询改写和HyDE文档生成互不依赖，但当前串行执行
- 理论上可并行，节省~3秒

## 三、优化方案

### 方案 #1: 重排性能优化 (P0, 预期收益 -22秒)

#### 3.1.1 切换到更快的重排模型

**当前配置:**
```python
COARSE_RERANK_MODEL = "bge-reranker-large"  # 1024维
FINE_RERANK_MODEL = "bge-reranker-large"
```

**优化方案:**
```python
COARSE_RERANK_MODEL = "bge-reranker-v2-m3"  # 更快，性能相当
FINE_RERANK_MODEL = "bge-reranker-base"     # 精排用base即可
```

**预期效果:**
- 粗排: 15秒 → 5秒 (-10秒)
- 精排: 20秒 → 8秒 (-12秒)
- **总收益: -22秒**

**实施难度**: 低（修改配置 + 模型下载）

---

#### 3.1.2 批量推理优化

**当前实现:**
```python
# app/core/retrieval/rerank.py (推测)
for chunk in chunks:
    score = model.predict(query, chunk.content)  # 逐个推理
```

**优化方案:**
```python
# 批量推理
batch_size = 8  # 粗排
scores = model.predict_batch(query, [c.content for c in chunks], batch_size=batch_size)

batch_size = 4  # 精排
scores = model.predict_batch(query, [c.content for c in chunks], batch_size=batch_size)
```

**预期效果:**
- 粗排: 5秒 → 3秒 (-2秒，在模型切换基础上)
- 精排: 8秒 → 5秒 (-3秒)
- **额外收益: -5秒**

**实施难度**: 中（需修改rerank模块批处理逻辑）

---

#### 3.1.3 启用L3重排缓存

**当前状态:**
- `cache.get_rerank()` / `cache.set_rerank()` 已实现
- 但实际日志中未见cache hit

**检查点:**
```python
# 检查缓存key生成逻辑
cache_key = f"rerank:{query_hash}:{chunk_ids_hash}"
# 确认Redis连接正常
# 确认TTL设置合理（建议30分钟）
```

**预期效果:**
- 首次查询: 无收益
- 重复查询: -35秒（完全跳过重排）

**实施难度**: 低（调试现有缓存逻辑）

### 方案 #2: 召回过滤策略优化 (P1, 预期收益 -9秒)

#### 3.2.1 Soft Filter（推荐）

**当前策略:**
```python
# ES查询
"filter": [{"term": {"category": "配电"}}]  # must，强制过滤
```

**优化方案:**
```python
# 改为should，不强制过滤但提升匹配项权重
"should": [{"term": {"category": "配电", "boost": 2.0}}]
"minimum_should_match": 0
```

**预期效果:**
- 避免0结果: category文档少时仍能召回其他类别
- 保留排序优势: 匹配category的文档分数更高
- **收益: -9秒**（避免第一轮失败 + filter relaxation）

**实施难度**: 中（修改 `recall.py` 和 `search_engine.py`）

---

#### 3.2.2 置信度阈值门控

**优化方案:**
```python
def build_filters(category: str, confidence: float) -> dict:
    if confidence < 0.95:
        logger.info(f"Category confidence {confidence} < 0.95, skipping filter")
        return {}
    return {"category": category}
```

**预期效果:**
- 低置信度时不过滤，减少误判
- 高置信度时过滤，保证精准度

**实施难度**: 低

---

#### 3.2.3 预检查策略

**优化方案:**
```python
# 在召回前快速检查category文档数
doc_count = db.query(Document).filter(category=category).count()
if doc_count < 10:
    logger.warning(f"Category {category} has only {doc_count} docs, skipping filter")
    filters = {}
```

**预期效果:**
- 提前避免0结果
- 减少不必要的召回重试

**实施难度**: 低

### 方案 #3: 预处理去重 (P1, 预期收益 -3.5秒)

**问题根因:**
- 前端调用 `/query/preprocess` 展示澄清界面（3.5秒）
- 用户提交后，`/query` 内部又调用一次预处理（3.5秒）

**优化方案A: 前端传递预处理结果（推荐）**

```python
# backend/app/schemas/query.py
class QueryRequest(BaseModel):
    query: str
    preprocessing_result: Optional[PreprocessResponse] = None  # 新增

# backend/app/services/query_service.py
async def execute_query(self, ...):
    if request.preprocessing_result:
        preprocessing_output = request.preprocessing_result
        logger.info("[User] Using cached preprocessing result")
    else:
        preprocessing_output = await self.preprocessor.preprocess(...)
```

```typescript
// frontend/src/hooks/useConversation.ts
const response = await executeQuery({
  query: snapshot.query,
  preprocessing_result: snapshot.preprocess,  // 传递预处理结果
  refined_query: snapshot.refinedQuery,
  // ...
})
```

**预期效果:**
- 避免重复LLM调用: -3.5秒
- 保证结果一致性

**实施难度**: 中（需前后端配合）

---

**优化方案B: 服务端缓存（备选）**

```python
# 在预处理时写入Redis缓存
cache_key = f"preprocess:{query_hash}:{user_id}"
cache.set(cache_key, preprocessing_result, ttl=300)

# 在query service中优先读取缓存
cached = cache.get(cache_key)
if cached:
    preprocessing_output = cached
```

**预期效果:**
- 同样避免重复调用: -3.5秒

**实施难度**: 低

### 方案 #4: HyDE并行化 (P2, 预期收益 -3秒)

**当前实现:**
```python
# 串行执行
expanded_queries = await self.rewriter.decompose(query)  # 2.6s
hyde_doc = await self.hyde.generate(query, category)    # 6.6s
```

**优化方案:**
```python
# 并行执行
async def parallel_rewrite_and_hyde():
    decompose_task = self.rewriter.decompose(query)
    hyde_task = self.hyde.generate(query, category)
    expanded_queries, hyde_doc = await asyncio.gather(decompose_task, hyde_task)
    return expanded_queries, hyde_doc

# 调用
expanded_queries, hyde_doc = await parallel_rewrite_and_hyde()
```

**预期效果:**
- 总耗时从 9秒（2.6+6.6）降至 6.6秒（取max）
- **收益: -2.4秒**

**实施难度**: 低

## 五、风险与注意事项

### 5.1 模型切换风险

**风险:**
- `bge-reranker-v2-m3` 精度可能略低于 `bge-reranker-large`

**缓解措施:**
1. A/B测试对比精度（基于历史查询测试集）
2. 监控上线后的答案质量（feedback_score）
3. 必要时回滚或采用混合策略（粗排用m3，精排用large）

### 5.2 Soft Filter风险

**风险:**
- category匹配度下降，召回噪声增加

**缓解措施:**
1. 设置合理的boost权重（2.0）
2. 监控召回相关性指标（rerank后top8的category分布）
3. 与置信度阈值门控结合使用

### 5.3 预处理去重风险

**风险:**
- 前端传递的preprocessing_result可能过期或被篡改

**缓解措施:**
1. 添加时间戳校验（结果生成时间<5分钟）
2. 后端重新验证关键字段（normalized_query, lane_suggestion）
