# PDF到知识库流程设计概要

**文档版本**: v1.0  
**创建日期**: 2026-07-09  
**状态**: 设计概要

---

## 一、问题诊断

### 当前问题

1. **表格被切碎**：按行解析，丢失表头和上下文
2. **元数据缺失**：标准号、条款号等字段未提取
3. **图片未处理**：技术图纸被跳过，无法检索
4. **分块简陋**：固定字符切分，条款被截断

---

## 二、设计目标

### 质量目标
- 表格完整性：作为整体保存，包含表头、所有行、标题
- 元数据准确性：标准号、条款号准确率 ≥95%
- 分块语义完整：每个chunk包含完整语义单元
- 图片可检索：支持"图XX所示"查询
- 引用关联：识别"见5.1条"等引用

### 性能目标
- 单个标准（50页）处理 ≤ 5分钟
- 支持批量处理和增量更新

---

## 三、整体架构

### 6步处理流水线

```
PDF文档
  ↓
Step 1: 文档解析
  - PyMuPDF/pdfplumber提取文本、表格、图片
  - 识别版面结构
  - 保留完整表格结构
  ↓
Step 2: 结构化分块
  - 国家标准按条款切分
  - 父块（512-1024 token）+ 子块（128-256 token）
  - 表格独立成块
  - 图片与说明绑定
  ↓
Step 3: 元数据提取
  - 正则提取：标准号、条款号、电压等级
  - LLM分类：类别、知识类型
  - 引用关系解析
  ↓
Step 4: 向量化
  - 稠密向量：bge-large-zh-v1.5
  - 稀疏向量：efficient-splade
  ↓
Step 5: 三库并行写入
  - Qdrant：向量 + payload
  - Elasticsearch：BM25全文检索
  - MySQL：元数据 + 关系
  ↓
Step 6: MinIO存储
  - 原始PDF
  - 提取的图片
```

## 四、核心设计方案

### 4.1 文档解析层

#### 4.1.1 简单表格处理
- 使用pdfplumber的`extract_tables()`提取二维数组
- 保留完整表头和所有行
- 转换为Markdown格式

#### 4.1.2 复杂表格处理（合并单元格）

**存储方案**：JSON单一数据源

**数据结构**：
```json
{
  "title": "表5-1 检验项目表",
  "headers": ["序号", "检验项目", "技术要求"],
  "rows": [["1", "充电时间", "5.4"]],
  "merges": [
    {"row": 0, "col": 0, "rowspan": 2, "colspan": 1}
  ]
}
```

**处理策略**：
1. pdfplumber提取原始表格（合并格后续为空）
2. 检测合并单元格（连续空格）
3. JSON记录合并信息
4. 按需生成Markdown（用于检索）

**为何选JSON**：
- 数据一致性：单一数据源
- 灵活性：可生成Markdown/HTML/CSV
- 结构化：显式记录合并信息

#### 4.1.3 图片处理（图文混合chunk）

**方案**：VLM描述 + OCR标注 + 文本向量检索

**处理流程**：
1. 提取PDF图片，保存到本地
2. VLM生成专业描述（Qwen2.5-VL-7B，离线）
3. OCR识别图中标注（PaddleOCR）
4. 组合文本：标题 + VLM描述 + OCR文字 + 上下文
5. 上传MinIO，记录URL

**chunk结构**：
```
chunk_type: "image"
text: VLM描述 + OCR标注 + 说明文字（用于向量检索）
image_path: MinIO URL
metadata: {caption, page_number, has_image}
```

**为何不用ColPali**：
- 系统需要句子级引用，ColPali只返回页面级
- 查询时无需GPU，成本低
- 现有架构无需改动

#### 4.1.4 公式处理

**分层策略**：

| 类型 | 方案 |
|-----|------|
| 简单公式 | 保留LaTeX，直接索引 |
| 复杂公式 | LaTeX + 自然语言描述 |
| 公式图片 | VLM描述 + 图片保存 |

**处理方式**：
1. 提取LaTeX公式
2. LLM生成自然语言描述（"短路电流等于电压除以阻抗"）
3. chunk包含：标题 + 描述 + LaTeX + 变量说明

**为何加描述**：
- LaTeX符号缺乏语义，向量检索效果差
- 自然语言可被语义检索
- 保留LaTeX，前端可渲染

---

### 4.2 智能分块层

#### 4.2.1 国家标准分块（条款粒度）

**层级结构**：章 → 节 → 条 → 款 → 项

**分块原则**：
- **父块**：完整章节（≤800 token），包含该章所有条款
- **子块**：单个条款（≤256 token），包含条款号、标题、正文

**Token限制（硬约束）**：
```
MAX_PARENT_TOKENS = 800   # bge-large-zh-v1.5有效窗口512
MAX_CHILD_TOKENS  = 256
```

**为何限制token**：
- bge-large-zh-v1.5超过512 token后向量质量下降
- 留20%余量给特殊字符

**处理流程**：
1. 按章节拆分
2. 提取章节下所有条款
3. 按token限制将条款分组为多个父块
4. 每个条款生成子块，关联到父块

**父子关系存储**：
- `parent_chunk_id`：存于子块（Qdrant + MySQL）
- 父块包含哪些子块：**仅存MySQL**，通过FK反查

#### 4.2.2 表格分块策略

**核心原则**：表格作为独立chunk，不切分

**为何独立**：
- 表格是整体语义单元
- 用户查询"检验项目有哪些"应召回整个表格
- 前端可直接渲染

**chunk结构**：
```
chunk_type: "table"
text: Markdown表格（用于向量检索）
metadata: {
  table_title,
  table_data: JSON结构（前端精确渲染）,
  has_merged_cells,
  row_count, col_count
}
```

#### 4.2.3 图片分块策略

**核心原则**：图片与说明文字绑定成块

**组成**：
1. 图片标题
2. VLM生成的语义描述
3. OCR提取的图中标注
4. 前后文说明文字
5. MinIO图片URL

**检索流程**：
```
用户查询："三相插头怎么接线？"
  ↓ 向量检索
命中图文chunk（VLM描述匹配）
  ↓ LLM生成答案
引用原图：[查看原图](minio://...)
```

#### 4.2.4 公式分块策略

**核心原则**：LaTeX + 自然语言描述

**chunk组成**：
- 公式标题
- 自然语言描述（用于语义检索）
- 文本表达式（I_k = U_n / sqrt(3) × Z）
- LaTeX原文（前端渲染）
- 变量说明
- 适用条件

---

### 4.3 元数据提取层

#### 4.3.1 元数据字段定义

**必需字段**：
```
文档信息：doc_id, doc_title, doc_type, standard_no, version, status
分类信息：category, sub_category, voltage_level, knowledge_type
位置信息：chunk_id, chunk_type, page_number, chapter, clause
权重：importance_score
文本：text
```

#### 4.3.2 提取策略

| 字段 | 方法 | 工具 |
|-----|------|------|
| standard_no | 正则匹配 | 规则 |
| clause | 正则匹配 | 规则 |
| voltage_level | 正则匹配 | 规则 |
| category | LLM分类 | 豆包Pro |
| knowledge_type | LLM分类 | 豆包Pro |

**正则提取**：
- 标准号：`GB\s*\d+-\d+`
- 条款号：`\d+\.\d+(\.\d+)*`
- 电压等级：`\d+k?V`

**LLM分类**：
- 多标签分类
- 提示词包含电力领域术语

## 六、关键设计决策

### 决策1：图片处理 - 图文混合chunk vs ColPali

**选择**：图文混合chunk

**理由**：
- 需要句子级引用（ColPali只返回页面级）
- 查询时无需GPU，成本低
- VLM描述仅入库时执行一次

### 决策2：公式处理 - LaTeX + 自然语言描述

**理由**：
- LaTeX符号缺乏语义
- 自然语言可被语义检索
- 保留LaTeX供前端渲染

### 决策3：表格分块 - 独立成块 vs 拆分行

**选择**：独立成块

**理由**：
- 表格是整体语义单元
- 拆开会丢失表头和列关系
- 前端可直接渲染

### 决策4：复杂表格存储 - JSON vs HTML+Markdown

**选择**：JSON单一数据源

**理由**：
- 数据一致性：避免HTML与Markdown不同步
- 灵活性：可生成多种格式
- 结构化：显式记录合并信息

### 决策5：VLM模型 - Qwen2.5-VL-7B

**理由**：
- 中文技术图纸理解好
- 电力专业术语准确
- 入库时已用GPU，无额外成本
