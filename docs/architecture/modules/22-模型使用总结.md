# 模型使用总结

本文档总结了整个RAG系统中各个环节需要使用的AI模型，包括嵌入模型、重排模型、生成模型等。

---

## 一、模型使用概览

### 1.1 模型分类

| 模型类别 | 用途 | 典型模型 | 调用场景 |
|---------|------|---------|---------|
| 嵌入模型（稠密） | 文本向量化、语义检索 | bge-large-zh-v1.5 | 文档入库、查询向量化 |
| 嵌入模型（稀疏） | 关键词匹配、混合检索 | BM42/SPLADE | 向量库混合检索 |
| 重排模型 | 检索结果精排 | bge-reranker-large | 快车道两阶段重排 |
| 生成模型（主力） | 答案生成 | 豆包Pro/通义千问 | 最终答案生成 |
| 轻量级判别模型 | 快速分类判断 | 小型分类器 | 充分性判断、笼统度评分 |

### 1.2 模型调用频率统计

| 环节 | 每次查询调用次数 | 延迟要求 | 成本占比 |
|-----|----------------|---------|---------|
| 查询向量化 | 1-3次（查询扩展） | <100ms | 低 |
| 文档向量召回 | 1次 | <200ms | 低 |
| 重排（粗排） | 1次 | <50ms | 低 |
| 重排（精排） | 1次 | <100ms | 低 |
| 充分性判断 | 1次 | <100ms | 低 |
| 查询改写/HyDE | 0-2次（按需） | <200ms | 中 |
| 答案生成 | 1次 | <1000ms | **高** |
| 笼统度评估 | 0-1次（按需） | <200ms | 中 |

**成本结论**：答案生成（LLM调用）占总成本的70%+，是主要优化目标。

## 二、各环节模型使用详解

### 2.0 知识加工阶段（文档入库）

**阶段特点**：离线批处理、延迟不敏感、成本敏感、准确率优先。

#### 2.0.1 文档解析（无需AI模型）
- **模块**：`app.tasks.document_tasks`
- **工具**：PyMuPDF, pdfplumber, PaddleOCR（扫描版PDF）
- **说明**：PDF → Markdown，公式识别用 LaTeX-OCR，纯工程实现

#### 2.0.2 专业分类（语义任务）
- **模块**：`core.preprocessing.metadata_extractor.llm_classify_multilabel()`
- **任务性质**：多标签语义分类（一个条款可能属于"配电+防雷"），规则关键词匹配易漏判/误判
- **模型选择**：
  - **方案1（MVP推荐）**：**豆包Pro / 通义千问** Few-shot 多标签分类
    - 输入：条款文本（256~512 token）
    - 输出：主分类 + 相关分类列表 + 知识类型
    - Prompt：列举候选标签（配电/变电/继保/高压/输电/防雷/接地），Few-shot示例
    - 优点：无需标注数据即可上线
    - 成本优化：**批量调用**（50条/批）摊薄API费用；缓存结果供后续版本复用
  - **方案2（进阶降本）**：**bge-large-zh-v1.5**（已有）编码 + 轻量分类头
    - 训练数据：用方案1积累的LLM标注结果（2000+样本）
    - 模型：冻结 bge 编码器，训练 2层MLP/逻辑回归多标签分类头
    - 优点：复用现有嵌入模型，推理成本接近零，无新增模型依赖
    - 何时切换：积累足够标注数据后（约2000~5000样本）
- **调用时机**：文档入库时，每个文档块调用1次
- **调用量级**：假设5000文档×50块 = 25万次（批量调用分摊，实际API调用 ~5000次）
- **降级策略**：规则用于分类结果的快速校验（如"标准号含 GB 50057 → 必含防雷标签"）

#### 2.0.3 语义分块边界检测（专业书籍）
- **模块**：`core.preprocessing.semantic_chunk.detect_similarity_drops()`
- **任务性质**：判断"相邻段落是否属于同一知识点"（国家标准用条款规则切分，无需此步骤）
- **模型选择**：
  - **主要方法**：**bge-large-zh-v1.5**（已有）计算相邻段落余弦相似度
    - 输入：相邻两段文本（各128~256 token）
    - 输出：余弦相似度（0~1）
    - 边界判定：相似度骤降点（如从0.85跌至0.55）即语义边界
    - 算法：Semantic Chunking / Text Tiling
    - 优点：复用文档入库时已加载的嵌入模型，零额外成本，无新增依赖
  - **边界确认（兜底）**：**豆包Pro** 仅处理相似度接近阈值的"不确定边界"
    - 输入：边界附近的段落对（相似度在 0.5~0.7 之间）
    - 输出：合并 / 切分
    - 调用量：仅5~10%的边界需要LLM确认，大部分由相似度阈值直接决定
- **调用时机**：仅处理专业书籍类文档（标准类文档按条款切分，无需语义检测）
- **调用量级**：假设1000本书×50节×10次边界判断×10% LLM确认 = 5万次嵌入 + 5千次LLM
- **公式/图表保护**：规则（正则检测公式边界，强制完整性）

#### 2.0.4 向量化（入库核心）
- **模块**：`core.embedding.embedder`
- **模型**：
  - **稠密向量**：**bge-large-zh-v1.5**（1024维，本地GPU推理）
  - **稀疏向量**：**BM42 / SPLADE**（稀疏字典，本地GPU推理）
- **调用时机**：每个**父块**生成双向量（子块仅存文本，不生成向量）
- **调用量级**：假设5000文档×50节 = 25万父块
- **批处理**：batch_size=32，充分利用GPU
- **延迟**：单块 <50ms，批量处理吞吐 >200块/秒

### 2.1 查询预处理阶段

**阶段特点**：在线实时、延迟敏感、成本敏感。

#### 2.1.1 术语标准化（无需模型）
- **模块**：`core.preprocessing.term_normalizer`
- **方法**：规则引擎 + 术语词典
- **无AI模型调用**

#### 2.1.2 笼统度评估
- **模块**：`core.preprocessing.query_optimizer.assess_vagueness()`
- **模型选择**：
  - **方案1（推荐）**：轻量级分类模型（Few-shot学习）
    - 模型：基于BERT微调的二分类器
    - 输入：查询文本
    - 输出：笼统度评分（0-1）
    - 优点：快速、成本低
  - **方案2**：LLM Few-shot判断
    - 模型：豆包Pro/通义千问
    - 优点：准确率高、无需训练
    - 缺点：延迟高、成本高
- **调用时机**：每次查询（如果启用提问优化）
- **降级策略**：高峰期降级到规则引擎（关键词匹配）

#### 2.1.3 查询改写与扩展
- **模块**：`core.preprocessing.query_rewriter`
- **模型选择**：
  - **同义改写**：LLM生成（豆包Pro）
    - Prompt：生成2-3个专业同义问法
    - 延迟：~150ms
  - **HyDE假设文档生成**：LLM生成
    - Prompt：生成假设的专业解答（200字）
    - 用途：用假设答案的向量做检索
    - 适用场景：原理类/模糊问题
- **调用时机**：快车道预处理阶段（每次查询）
- **优化**：
  - 缓存热门查询的改写结果
  - 高峰期禁用查询扩展（降级）

#### 2.1.4 元数据提取（无需模型）
- **模块**：`core.preprocessing.metadata_extractor`
- **方法**：正则表达式 + 关键词匹配
- **无AI模型调用**

---

### 2.2 检索阶段（快车道）

#### 2.2.1 查询向量化
- **模块**：`core.embedding.embedder.encode_dense()`
- **模型**：**bge-large-zh-v1.5**
  - 维度：1024维
  - 部署：本地GPU推理（vLLM/TorchServe）
  - 批处理：支持batch推理
- **调用次数**：1-3次（原查询 + 扩展查询）
- **延迟**：单次 <50ms，批量 <100ms

#### 2.2.2 稀疏向量生成
- **模块**：`core.embedding.embedder.encode_sparse()`
- **模型**：**BM42** 或 **SPLADE**
  - 输出：{token_id: weight}稀疏字典
  - 用途：与稠密向量混合检索
- **调用时机**：与稠密向量同时生成
- **延迟**：<30ms

#### 2.2.3 向量召回（Qdrant）
- **模块**：`storage.vector_store.QdrantClient.hybrid_search()`
- **模型使用**：查询向量（预生成）
- **检索算法**：HNSW（向量库内置，非AI模型）
- **无额外模型调用**

#### 2.2.4 全文检索（Elasticsearch）
- **模块**：`storage.search_engine.ElasticsearchClient.bm25_search()`
- **算法**：BM25（传统检索算法，非AI模型）
- **无模型调用**

#### 2.2.5 结构化召回（MySQL）
- **模块**：数据库直接查询
- **无模型调用**

#### 2.2.6 两阶段重排
- **模块**：`core.retrieval.rerank.TwoStageReranker`
- **模型使用**：
  - **粗排**：轻量级重排模型
    - 模型：bge-reranker-base（小模型）
    - 输入：Top50候选
    - 输出：Top20
    - 延迟：<50ms
  - **精排**：**bge-reranker-large**
    - 输入：Top20候选
    - 输出：Top5-8
    - 延迟：<100ms
- **部署**：本地GPU推理
- **优化**：批量计算相似度

#### 2.2.7 召回充分性判断
- **模块**：`core.retrieval.sufficiency.SufficiencyChecker`
- **模型选择**：
  - **方案1（推荐）**：轻量级判别模型
    - 输入：查询 + Top5块的摘要
    - 输出：充分/不充分（二分类）
    - 延迟：<100ms
  - **方案2**：LLM快速判断
    - 模型：豆包Pro
    - Prompt：判断召回结果是否充分回答问题
    - 延迟：~100ms
    - 成本：略高
- **调用时机**：快车道首轮检索后
- **降级策略**：高峰期简化判断逻辑（规则引擎）

#### 2.2.8 二次检索查询改写
- **模块**：`core.preprocessing.query_rewriter.refine_query()`
- **模型**：LLM生成（豆包Pro）
- **Prompt**：基于首轮召回结果，补充缺失维度
- **调用时机**：充分性判断为"不充分"时（约20%查询）
- **延迟**：~150ms

---

### 2.3 检索阶段（慢车道）

#### 2.3.1 模型决策（多跳推理）
- **模块**：`core.retrieval.slow_lane.SlowLaneRetriever`
- **模型**：**LLM工具调用**（豆包Pro/通义千问）
- **能力要求**：
  - 支持Function Calling / Tool Use
  - 推理能力强
- **调用流程**：
  1. 模型分析查询，决定调用哪个工具
  2. 执行工具（调用快车道/数据库）
  3. 模型评估结果是否充分
  4. 重复最多3步
- **每步延迟**：~200-500ms
- **总延迟**：2-4秒（按步骤数）
- **成本**：较高（多次LLM调用）

#### 2.3.2 工具执行
- **工具1**：`_retrieve_standard()` → 调用快车道（复用嵌入/重排模型）
- **工具2**：`_retrieve_clause()` → MySQL直接查询（无模型）
- **工具3**：`_list_related_standards()` → MySQL聚合查询（无模型）

### 2.4 生成阶段

#### 2.4.1 答案生成
- **模块**：`core.generation.generator.AnswerGenerator`
- **模型**：**豆包Pro / 通义千问**（生成大模型）
- **能力要求**：
  - 支持长上下文（8k+ tokens）
  - 指令遵循能力强
  - 支持流式输出
- **输入**：
  - 用户查询
  - 检索到的Top5-8文档块
  - System Prompt（要求引用标注）
- **输出**：带引用的专业答案
- **延迟**：
  - 非流式：800-1200ms
  - 流式：首token <200ms
- **成本**：**最高**（占总成本70%+）

#### 2.4.2 引用溯源（无需模型）
- **模块**：`core.generation.citation.extract_citations()`
- **方法**：正则表达式提取引用标注
- **无AI模型调用**

#### 2.4.3 事实一致性校验（可选）
- **模块**：`core.generation.generator`（可选功能）
- **模型**：LLM二次验证 或 专用一致性模型
- **用途**：检查答案是否与参考资料一致
- **调用时机**：高价值查询或用户标记质疑时
- **延迟**：~300ms
- **当前状态**：待实现

### 2.5 闭环优化阶段

#### 2.5.1 Prompt优化（离线任务）
- **模块**：`celery任务: prompt_optimization_loop`
- **模型**：LLM批量分析
- **用途**：
  - 分析误判/漏判case
  - 生成Few-shot样本
  - 评估样本质量
- **调用频率**：每周1次（批量处理50-100条）
- **成本**：低（离线批量）

#### 2.5.2 术语扩展（离线任务）
- **模块**：`celery任务: terminology_expansion_loop`
- **模型**：LLM批量提取
- **用途**：识别用户补充的专业术语
- **调用频率**：每周1次（批量处理50条）
- **成本**：低

#### 2.5.3 难例分析（离线任务）
- **模块**：`celery任务: badcase_analysis_loop`
- **模型**：LLM根因分类
- **用途**：分析召回失败原因
- **调用频率**：每周1次
- **成本**：低

## 三、模型部署方案

### 3.1 本地部署模型（GPU推理）

| 模型 | 部署方式 | GPU要求 | 并发能力 |
|-----|---------|--------|---------|
| bge-large-zh-v1.5（嵌入） | vLLM / TorchServe | 1×16GB | 批量100/s |
| bge-reranker-large（精排） | TorchServe | 1×16GB | 批量50/s |
| bge-reranker-base（粗排） | TorchServe | 1×8GB | 批量100/s |

**优点**：
- 延迟低（<100ms）
- 成本低（无API调用费用）
- 数据不出内网

**部署要求**：
- GPU服务器：推荐 NVIDIA A10/T4/3090
- 模型预热：启动时加载到GPU
- 批处理优化：聚合请求，批量推理

### 3.2 API调用模型（LLM生成）

| 模型 | 供应商 | 用途 | 成本估算 |
|-----|-------|------|---------|
| 豆包Pro | 字节跳动 | 答案生成、多跳推理 | ¥0.8/千tokens |
| 通义千问 | 阿里云 | 答案生成（备选） | ¥0.6/千tokens |

**优点**：
- 无需自建GPU
- 模型持续升级
- 扩展性强

**成本控制**：
- 缓存热门查询结果（命中率目标60%+）
- 高峰期降级策略（禁用部分LLM调用）
- 成本监控告警（日成本>3500元触发降级）

## 四、模型调用链路示例

### 4.1 标准查询（快车道）

```
用户输入："10kV配电室安全距离要求"

1. 预处理阶段
   - 笼统度评估：轻量级分类模型 → 评分0.2（明确）
   - 查询改写：LLM生成 → 2个同义问法
   ├─ 模型调用：1次LLM（150ms）

2. 向量化阶段
   - 稠密向量：bge-large-zh-v1.5 → 1024维向量 × 2
   - 稀疏向量：BM42 → 稀疏字典 × 2
   ├─ 模型调用：1次嵌入（批量，80ms）

3. 召回阶段
   - 向量召回：Qdrant混合检索（无模型调用）
   - 关键词召回：Elasticsearch BM25（无模型调用）
   - 结构化召回：MySQL查询（无模型调用）
   ├─ 召回50个候选

4. 重排阶段
   - 粗排：bge-reranker-base → Top50 → Top20
   - 精排：bge-reranker-large → Top20 → Top5
   ├─ 模型调用：2次重排（共120ms）

5. 充分性判断
   - 轻量级判别模型 → 判断"充分"
   ├─ 模型调用：1次判别（80ms）

6. 答案生成
   - 豆包Pro → 生成带引用的答案
   ├─ 模型调用：1次LLM（900ms）

总模型调用：3次LLM + 3次嵌入/重排/判别
总延迟：~1.5秒
总成本：~0.003元/次（主要是LLM生成）
```

### 4.2 复杂查询（慢车道）

```
用户输入："GB 50057和DL/T 621对接地电阻要求有何差异"

1. 预处理阶段（同快车道）
   ├─ 模型调用：1次LLM（150ms）

2. 路由决策
   - 检测"对比"关键词 → 路由到慢车道

3. 多跳推理（慢车道）
   步骤1：LLM决策 → 调用 retrieve_standard("GB 50057", "接地电阻")
          ├─ 执行快车道检索（复用嵌入/重排模型）
          ├─ 模型调用：1次LLM决策 + 嵌入/重排（400ms）
   
   步骤2：LLM决策 → 调用 retrieve_standard("DL/T 621", "接地电阻")
          ├─ 执行快车道检索
          ├─ 模型调用：1次LLM决策 + 嵌入/重排（400ms）
   
   步骤3：LLM决策 → 评估"充分"，停止检索
          ├─ 模型调用：1次LLM决策（200ms）

4. 答案生成（对比两个标准）
   - 豆包Pro → 生成对比分析
   ├─ 模型调用：1次LLM（1200ms）

总模型调用：5次LLM + 2轮嵌入/重排
总延迟：~3.5秒
总成本：~0.008元/次
```

## 五、成本优化策略

### 5.1 缓存策略（降低模型调用）

| 缓存内容 | TTL | 预期命中率 | 节省成本 |
|---------|-----|-----------|---------|
| 查询结果缓存 | 1小时 | 60%+ | 节省60% LLM调用 |
| 向量缓存 | 24小时 | 80%+ | 节省80% 嵌入调用 |
| 笼统度评估缓存 | 1小时 | 70%+ | 节省70% 判别调用 |
| 查询改写缓存 | 1小时 | 50%+ | 节省50% LLM调用 |

**预期总成本降低**：40-50%

### 5.2 高峰降级策略

**触发条件**：QPS > 80 或 日成本 > 3500元

**降级措施**：
1. **笼统度评估**：降级到规则引擎（无LLM调用）
2. **查询改写**：禁用（减少扩展查询数量）
3. **充分性判断**：简化为规则判断（无模型调用）
4. **慢车道**：限流到QPS=3
5. **缓存TTL**：延长到3小时

**预期成本降低**：30%

### 5.3 批量推理优化

- **嵌入模型**：聚合100ms内的请求，批量推理

### 6.1 为什么选择 bge-large-zh-v1.5？

| 模型 | 维度 | 中文性能 | 部署难度 | 决策 |
|-----|------|---------|---------|-----|
| bge-large-zh-v1.5 | 1024 | ⭐⭐⭐⭐⭐ | 简单 | ✅ 选用 |

| OpenAI text-embedding-3 | 1536 | ⭐⭐⭐⭐ | 简单（API） | 成本高 |

**决策理由**：
- 中文电力专业文本效果最佳
- 社区活跃，文档完善
- 支持本地部署，延迟可控
- 支持混合检索（配合BM42）

### 6.2 为什么选择 bge-reranker-large？

**重排模型选型对比**：

| 模型 | 参数量 | 精度 | 延迟 | 决策 |
|-----|--------|------|------|-----|
| bge-reranker-large | 326M | ⭐⭐⭐⭐⭐ | ~100ms | ✅ 选用（精排） |
| bge-reranker-base | 102M | ⭐⭐⭐⭐ | ~50ms | ✅ 选用（粗排） |
| cross-encoder | 278M | ⭐⭐⭐⭐ | ~120ms | 备选 |

**决策理由**：
- 两阶段重排兼顾精度和速度
- 粗排用base快速筛选，精排用large保证质量
- 满足延迟SLA（P95 < 3s）

### 6.3 为什么选择豆包Pro？

**生成模型选型对比**：

| 模型 | 成本 | 中文能力 | 工具调用 | 决策 |
|-----|------|---------|---------|-----|
| 豆包Pro | ¥0.8/千tokens | ⭐⭐⭐⭐⭐ | ✅ 支持 | ✅ 选用 |
| 通义千问 | ¥0.6/千tokens | ⭐⭐⭐⭐ | ✅ 支持 | 备选 |
| GPT-4 | ¥20/千tokens | ⭐⭐⭐⭐ | ✅ 支持 | 成本过高 |

**决策理由**：
- 中文专业领域生成质量高
- 支持Function Calling（慢车道必需）
- 成本适中，满足预算
- 通义千问作为备选（成本更低）
